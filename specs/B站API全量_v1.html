2. 鉴权体系

B 站没有统一的 OAuth。实际存在五套并行机制，同一批接口经常同时接受其中两三套：

1. Cookie（SESSDATA 为主）：Web 端的默认方式。 2. wbi 签名：Web 端的防爬参数签名，2023-03 起逐步铺开，和 Cookie 叠加使用。 3. appkey + appsec 签名：APP 端方式，参数签名 + access_key。 4. gRPC Metadata：APP 的 protobuf 通道，authorization: identify_v1 {access_key} 加一堆 x-bili-*-bin。 5. auth_key：仅用于静态资源（字幕 JSON），由播放器接口下发，自带过期时间。

2.2 Cookie 键逐个说

SESSDATA。整个鉴权的地基。登录成功时由 passport.bilibili.com 下发：


set-cookie: SESSDATA=***; Path=/; Domain=bilibili.com; Expires=Sat, 04 Mar 2023 07:30:09 GMT; HttpOnly; Secure

三个细节值得记住：HttpOnly 意味着前端 JS 读不到（所以只能从响应头或浏览器存储里取）；Domain=bilibili.com 而不是 www.bilibili.com，因此 api.*、live.*、space.* 全都能带；值本身是 URL 编码过的，内含 %2C（逗号）分隔的多段，直接拼接进 Cookie 头时不要二次编码，否则 -101。

SESSDATA 的有效期在响应里给（示例是半年量级），但服务端会提前因为改密码、异地登录、风控而作废。判断是否还有效的廉价办法是打 GET https://api.bilibili.com/x/web-interface/nav：code=0 且 data.isLogin=true 就是活着；code=-101 就是死了。这个接口同时也是 wbi 密钥的来源，一举两得。

bili_jct。32 位十六进制，所有写接口的 csrf 参数直接抄它。它与 SESSDATA 是绑定的：换号必须同时换。失效表现是 code=-111，而不是 -101——这是区分"没登录"和"csrf 没带对"的关键。POST 时 csrf 既可以放 query 也可以放表单体，文档里两种都有（docs/video/action.md 用表单，docs/fav/action.md 用 query）。

DedeUserID / DedeUserID__ckMd5。前者是数字 UID，后者是它的摘要。很多接口的鉴权条件写的是"Cookie 中 DedeUserID 存在且不为 0"（例如 docs/audio/action.md:11、docs/audio/music_list.md:11），这种情况下 SESSDATA 反而不是硬条件。做多账号池时，这两个值必须与 SESSDATA、bili_jct 成套替换，混搭会得到 -101 或直接 -352。

buvid3 / buvid4 / b_nut。见 2.4。要点是：buvid3 是设备身份，buvid4 是同一设备带时间片的第二标识，b_nut 是"这个 buvid 是哪天生的"。三者必须自洽，服务端会交叉校验。

buvid_fp。【文档未收录】整个 docs/ 里搜不到 buvid_fp 的生成说明，只有 docs/misc/buvid3_4.md 讲 buvid3/buvid4/b_nut。本次实测也印证了它的存在价值：只带 buvid3 + b_nut 打 /x/space/wbi/acc/info 依旧是 -352，而同一套请求在浏览器里正常。结论是它属于浏览器端指纹（Canvas/WebGL/字体/时区一类），由前端脚本算出后写入 Cookie，社区无公开算法。工程上的正确做法不是伪造它，而是用真实浏览器取一次 Cookie 再复用，或者接受空间类接口不可用。

_uuid。【文档未收录】前端生成，形如五段大写十六进制用 - 连接的设备 UUID，末段常带 infoc 尾巴。生成逻辑未公开，但因为它只在部分推荐/签名接口里参与，缺失时表现为推荐内容质量下降而不是报错，所以优先级低。

b_lsid。【文档未收录】单标签页会话标识，形如"8 位十六进制 + _ + 时间戳十六进制"。B 站用它区分同一账号下的多个标签页，写操作（尤其投币、点赞）短时间内来自不同 b_lsid 会被判异常。批量操作时固定一个 b_lsid 反而更安全。

CURRENT_FNVAL。播放器把用户上次选的清晰度写进这个 Cookie，值就是 fnval 的位掩码（16=DASH，80=1080P，4048=全部 DASH 特性）。它不参与鉴权，但服务端会读它来决定 playurl 的默认返回，做自动化取流时显式传 fnval 更可靠。

bili_ticket。JWT，alg=HS256、kid=s03，载荷里只有 exp、iat、plt 三个字段。算法见 docs/misc/sign/bili_ticket.md：取当前秒级时间戳 ts，用密钥 XgwSnGZ1p 对字符串 ts{timestamp} 做 hmac_sha256 得 hexsign，然后 POST https://api.bilibili.com/bapis/bilibili.api.ticket.v1.Ticket/GenWebTicket，参数 key_id=ec02、hexsign、context[ts]、csrf（可为空）。返回的 data.ticket 就是它，有效期 259200 秒。它不是必需项，但带上能明显降低 -352 概率，属于性价比很高的一步。

2.3.3 签名规则

1. 业务参数里加上 wts，值为秒级 UNIX 时间戳（不是毫秒，写错会 -352）。 2. 所有参数（含 wts）按 key 的 ASCII 升序排序。 3. 每个 value 先过滤掉字符 !'()*（这是文档明确要求的，目的是避开 URL 编码歧义）。 4. 用 encodeURIComponent 编码：空格编成 %20（不是 +），百分号后的十六进制大写。 5. 拼成 k=v&k=v 的 query 串，末尾直接拼 mixin_key，整体求 MD5，得到 32 位小写 w_rid。 6. 把 w_rid 追加到原始参数（未排序、未过滤的那份）后面发出去。

第 6 步是最容易错的地方：签名用排序后的串，发送用原始串。两者不一致不影响校验（服务端自己会排序），但如果你把过滤后的值发出去，业务参数就变形了。

2.3.4 可直接运行的实现


// wbi.js —— 无依赖，Node 18+ / 浏览器通用
const MIXIN_KEY_ENC_TAB = [
  46,47,18,2,53,8,23,32,15,50,10,31,58,3,45,35,
  27,43,5,49,33,9,42,19,29,28,14,39,12,38,41,13,
  37,48,7,16,24,55,40,61,26,17,0,1,60,51,30,4,
  22,25,54,21,56,59,6,63,57,62,11,36,20,34,44,52
];

const getMixinKey = (orig) =>
  MIXIN_KEY_ENC_TAB.map((n) => orig[n]).join('').slice(0, 32);

// 浏览器端可直接用 crypto.subtle；Node 端用 node:crypto 的 createHash
async function md5Hex(str) {
  const buf = new TextEncoder().encode(str);
  const digest = await crypto.subtle.digest('MD5', buf).catch(() => null);
  if (digest) {
    return [...new Uint8Array(digest)]
      .map((b) => b.toString(16).padStart(2, '0')).join('');
  }
  const { createHash } = await import('node:crypto');
  return createHash('md5').update(str).digest('hex');
}

async function encWbi(params, imgKey, subKey, now = Math.floor(Date.now() / 1000)) {
  const mixinKey = getMixinKey(imgKey + subKey);
  const wts = String(now);
  const all = { ...params, wts };
  const query = Object.keys(all)
    .sort()
    .map((k) => {
      const v = String(all[k]).replace(/[!'()*]/g, '');
      return `${encodeURIComponent(k)}=${encodeURIComponent(v)}`;
    })
    .join('&');
  const w_rid = await md5Hex(query + mixinKey);
  return { ...params, wts, w_rid };
}

2.3.6 v_voucher：被判定为机器时的下一步

来源 docs/misc/sign/v_voucher.md。当 wbi 校验不过或风控分超标，响应不再返回业务数据，而是给一个 v_voucher 字符串（同时出现在响应头 x-bili-gaia-vvoucher 和响应体 data.v_voucher）。后续流程：

1. POST https://api.bilibili.com/x/gaia-vgate/v1/register，带 v_voucher，换回一个极验 challenge； 2. 走极验拿 validate / seccode； 3. POST https://api.bilibili.com/x/gaia-vgate/v1/validate，换 grisk_id； 4. 把 grisk_id 带回原请求。

文档自己也承认这是最后手段（验证码需要人操作）。工程上更划算的顺序是：先补 buvid3/buvid4/b_nut/bili_ticket，再换 IP，最后才考虑验证码。

2.4 buvid 三件套

来源：docs/misc/buvid3_4.md、docs/misc/device_identity.md。buvid3 是 B 站风控的主键，没有它，空间、动态、搜索、直播弹幕这些接口会大面积 -352。

2.4.1 三条获取路径

路径一：接口直取 buvid3


GET https://api.bilibili.com/x/web-frontend/getbuvid

响应 data.buvid 就是一个 buvid3（不带别的）。这条接口本身不要求 Cookie，也不要求签名，最省事，但拿不到 buvid4 和 b_nut。

路径二：接口直取 buvid3 + buvid4


GET https://api.bilibili.com/x/frontend/finger/spi

响应：


{"code": 0, "message": "0", "ttl": 1,
 "data": {"b_3": "XXXX...infoc", "b_4": "XXXX...infoc"}}

b_3 就是 buvid3，b_4 就是 buvid4。文档明确提醒：不要复制示例里的值，自己生成或现取，示例值早被标记了。

路径三：首页响应头白拿（推荐）

GET 或 HEAD https://www.bilibili.com/，从 Set-Cookie 里捡：


set-cookie: buvid3=805E4894-96A2-0684-6F00-C6EA1FFB911023315infoc; path=/; expires=Sat, 26 Jul 2025 06:38:43 GMT; domain=.bilibili.com
set-cookie: b_nut=1721975923; path=/; expires=Sat, 26 Jul 2025 06:38:43 GMT; domain=.bilibili.com

这条路径有三个坑，文档都写了：

  • User-Agent 里不能出现 curl、python、awa 等子串，否则不下发；
  • 同一个 User-Agent 不得短时间多次请求，否则也不下发；
  • b_nut 的取值规则：不带 Cookie → 当前 UNIX 秒；只带 buvid3 → 100；只带 b_nut → 同"不带"；两个都带 → 没有 Set-Cookie。

第三条意味着：如果你已经有 buvid3 但没有 b_nut，正确做法是清掉 buvid3 重新要一次，而不是单独去求 b_nut——单独求只会拿到时间戳，配不上你那台"设备"。

2.4.2 buvid3 的结构

805E4894-96A2-0684-6F00-C6EA1FFB911023315infoc 这种形态：4-4-4-4-12 的十六进制分组（共 32 位有效 hex），后面跟一段数字，再跟 infoc 结尾。末尾数字段与生成时间有关，infoc 是来源标记。文档没有给出完整的 web 端生成算法（只给了 APP 端的 BUVID 算法，见下），所以自造 buvid3 属于"能过但危险"，会被判为新设备。

2.4.3 buvid4 与 buvid3 的区别

buvid4 是同一设备标识的第二版，长度更长，内含时间片信息。文档没有单独说明二者关系，只说"spi 一次给两个"。实测中两者都写进 Cookie 后，-352 出现率明显下降；只写 buvid3 时空间类接口仍然挂。工程结论：能拿两个就都带上。

2.4.4 buvid_fp 与 x/frontend/finger/activation

【未取全文】x/frontend/finger/activation 与 buvid_fp 在整个 docs/ 目录里没有独立文档。可以确认的是：

  • buvid_fp 存在于真实浏览器的 Cookie 里，值是一串 32 位十六进制；
  • 本次实测用 buvid3 + b_nut（无 buvid_fp）打 /x/space/wbi/acc/info，返回 -352，而浏览器同接口正常；
  • 因此它是"设备指纹"性质的加权项，而非鉴权必需项。

需要全文的话，可以按这几个方向找：docs/misc/device_identity.md（APP 端 fp 算法，含 fp_local/fp_remote 的完整构造步骤与 Rust 实现）、docs/misc/buvid3_4.md（web 端 buvid 说明）、以及 fork 仓库里对 finger 的 issue 讨论。

APP 端的 fp 算法文档给得很细，可以照抄：取 BUVID（XU 前缀），拼设备 Model、无线电固件版本，MD5 后接 yyyyMMddhhmmss，再接 16 位随机 hex，最后附两位校验码（把前 62 字符按两字符一组转 16 进制求和，对 256 取余）。这套东西用于 gRPC Metadata 的 x-bili-fawkes-req-bin 一族。

2.5 APP 端 appkey / appsec 签名

来源：docs/misc/sign/APP.md、docs/misc/sign/APPKey.md。规则比 wbi 简单，但坑在"表在变、key 会废"。

2.5.1 算法

1. 业务参数里加上 appkey； 2. 全部参数按 key 升序排序； 3. 拼成 k=v&k=v，value 做 urlencode； 4. 末尾直接拼上该 appkey 对应的 appsec； 5. 整体 MD5，小写 32 位，就是 sign； 6. 请求时把 sign 与 appkey 一起带上（appkey 不算进签名串之外的额外处理，它本身就在串里）。

文档自带可验证样例：appkey=1d8b6e7d45233436、appsec=560c52ccd288fed045859ed18bffd973，参数 id=114514、str=1919801、test=いいよ，こいよ，算出的 sign 应当是 01479cf20504d865519ac50f33ba3a7d。写实现时先拿这个用例对一遍，对不上就是排序或编码错了（注意 value 里有全角逗号和日文，编码必须 UTF-8）。

2.6 登录链路

来源：docs/login/login_action/QR.md、password.md、SMS.md、readme.md、docs/login/cookie_refresh.md。

2.6.1 扫码登录（唯一不需要处理验证码的方式）


GET https://passport.bilibili.com/x/passport-login/web/qrcode/generate

返回：


{"code": 0, "data": {
  "url": "https://passport.bilibili.com/h5-app/passport/login/scan?navhide=1&qrcode_key=8587cf8106a0b863c46d6bab913537f6&from=",
  "qrcode_key": "8587cf8106a0b863c46d6bab913537f6"}}

把 url 渲染成二维码给手机扫，同时每 2 秒左右轮询：


GET https://passport.bilibili.com/x/passport-login/web/qrcode/poll?qrcode_key=<key>

code 与 data.code 的组合含义：

| 状态 | code | data.code | 含义 | | --- | --- | --- | --- | | 成功 | 0 | 0 | 登录完成，data.url 是跨域跳转 URL，响应头带全套 Set-Cookie | | 待确认 | 0 | 86090 | 已扫码，手机还没点确认 | | 未扫码 | 0 | 86101 | 继续轮询 | | 已失效 | 0 | 86038 | 二维码过期，重新 generate |

成功时的 Set-Cookie 是四个：SESSDATA、bili_jct、DedeUserID、DedeUserID__ckMd5，外加 sid。响应体里还有 refresh_token（未登录时为空字符串），这个值要存下来，刷新 Cookie 时要用。

2.6.2 密码登录

四步，缺一步都不行：

1. 人机验证：GET https://passport.bilibili.com/x/passport-login/captcha?plat=web（新版）或 web/captcha/combine（旧版），拿 token、gt、challenge，走极验得 validate、seccode。 2. 取公钥与盐：GET https://passport.bilibili.com/x/passport-login/web/key，返回 data.hash（16 字符盐，有效期仅 20 秒）与 data.key（PEM 格式 RSA 公钥）。 3. 加密：把盐拼在明文密码前面（salt + password），用 RSA 公钥按 PKCS#1 v1.5 加密，再 base64。 4. 提交：POST https://passport.bilibili.com/x/passport-login/web/login，字段 username、password（上一步的 base64 密文）、keep、token、challenge、validate、seccode、go_url、source、csrf。

20 秒的盐有效期意味着"取 key → 加密 → 提交"必须一口气做完，中间卡住就得重取。这也是密码登录比扫码脆弱的根本原因。

2.6.3 短信登录

1. 人机验证（同上）； 2. POST https://passport.bilibili.com/x/passport-login/web/sms/send，字段 cid（国际区号，86 为中国大陆）、tel、csrf、login_session、recaptcha_token； 3. POST https://passport.bilibili.com/x/passport-login/web/login/sms，字段 cid、tel、code（短信码）、csrf、captcha_key、login_session。

国际区号表在 GET https://passport.bilibili.com/web/generic/country/list，返回 common 与 others 两组，每组元素是 {id, cname, country_id}。

APP 端对应的是 x/passport-login/sms/send 与 x/passport-login/login/sms（路径里少了 web/），参数形态不同，别混。

2.6.4 Cookie 刷新（保号的关键）

来源：docs/login/cookie_refresh.md。SESSDATA 会过期，但只要有 refresh_token 就能无感续命，不必重新扫码。流程五步：

1. 查是否需要刷：GET https://passport.bilibili.com/x/passport-login/web/cookie/info?csrf=<bili_jct>，返回 data.refresh（布尔）与 data.timestamp。 2. 算 CorrespondPath：文档给的是 RSA-OAEP 一类算法（附 Kotlin / Go / Java 三份 demo），输入是上一步的 timestamp，输出一串路径片段。 3. 取 refresh_csrf：GET https://www.bilibili.com/correspond/1/{CorrespondPath}，这是一个 SSR 页面，从 DOM 里 #1-name 节点取文本，就是 refresh_csrf。 4. 刷新：POST https://passport.bilibili.com/x/passport-login/web/cookie/refresh，字段 csrf（旧 bili_jct）、refresh_csrf、refresh_token、source=main_web。响应 Set-Cookie 给出新的SESSDATA、bili_jct、DedeUserID、DedeUserID__ckMd5、sid，响应体给出新的 refresh_token。 5. 确认：POST https://passport.bilibili.com/x/passport-login/web/confirm/refresh，字段是新 csrf 与旧 refresh_token。这一步的作用是让旧 token 失效，不做的话第 4 步的刷新不算完成。

错误码 86095 表示 refresh_csrf 错，或者 refresh_token 与当前 Cookie 不匹配——通常是因为第 4 步和第 5 步之间把新旧 token 搞混了。第 5 步必须用旧的，这是最容易反直觉的一处。

2.7 错误码与风控处置

来源：docs/misc/errcode.md。B 站把错误塞在 JSON 的 code 字段里，HTTP 状态码经常是 200。所以只看 HTTP 状态判断成败一定会错。

| code | 含义 | 现场处置 | | --- | --- | --- | | 0 | 成功 | — | | -1 | 应用不存在或被封禁 | 检查 appkey | | -2 | AccessKey 错误 | 重新登录 | | -3 | 密钥错误 | 检查 appsec | | -4 | 无权限 | 账号等级/权限不足 | | -101 | 未登录 | 补 SESSDATA，或确认其未过期 | | -102 | 账号被封停 | 换号 | | -104 | 硬币不足 | 业务层 | | -105 | 验证码错误 | 重走极验 | | -111 | csrf 校验失败 | 补 bili_jct，确认与 SESSDATA 同源 | | -112 | 系统升级中 | 等 | | -113 / -115 | 未实名认证 | 无法自动化 | | -304 | 无改动 | 幂等操作重复提交，非错误 | | -352 | 风控校验失败 | 见下 | | -400 | 请求错误 | 参数缺失 | | -401 | 未认证或非法请求 | 签名/凭据整段不对 | | -403 | 权限不足 | 例如 AI 摘要需登录 | | -404 | 资源不存在 | 路径写错或接口下线 | | -412 | IP 被风控拦截 | 换 IP，降频 | | -500 | 服务器错误 | 重试 | | -503 | 过载 | 退避 | | -509 | 超出限制 | 限流，按小时计 | | -625 | 登录失败次数过多 | 停手 | | -629 | 用户名或密码错误 | — | | -658 | Token 已过期 | 刷 access_key | | -688 | 地区限制 | 需对应地区 IP | | -689 | 版权限制 | 无解 | | -799 | 请求过于频繁 | 降频 |

-352 是日常最常见的敌人，本次实测撞了三次（空间信息、空间投稿、直播分区列表）。它是复合判定，可能的原因按修复成本排序：

1. User-Agent 不像浏览器（含 curl/python，或者是默认 Go-http-client）； 2. Referer 不是 https://www.bilibili.com/（必须精确到带尾斜杠）； 3. 缺 buvid3 / buvid4 / b_nut； 4. 缺 buvid_fp、_uuid、b_lsid； 5. wbi 签名缺失或算错； 6. 同 IP 频率过高。

-412 更硬：它不是 JSON 层的错误，而是网关直接把请求拦掉，返回体是一行纯文本 request was banned（本次实测动态空间接口就是这种）。到了 -412 说明 IP 已经被标记，继续打只会加重，正确做法是停手 + 换出口。

-509 和 -799 是限流，区别在于 -509 通常按小时窗口计（例如收藏夹批量操作），-799 是秒级频率。两者都只能退避。

逐条拆：

  • Bili-Status-Code：把业务 code 复制到响应头里。0 成功，-101 未登录，-352 风控。它对调试的价值在于：即使你把响应体丢进 /dev/null，看头就知道成败。
  • Bili-Trace-Id：16 位十六进制，单次请求的短 id。
  • X-Bili-Trace-Id：32 位十六进制，后 16 位就是 Bili-Trace-Id（...53ca2579dd6b045a）。前 16 位是上游链路 id。报障时给这个全长值最有用。
  • Cpu_usage：后端进程的 CPU 占用（这里是 114，单位不明，可能是个百分数乘以某系数）。它是观察服务端压力的免费信号，抓取时如果这个值持续走高，说明你在给对方添麻烦，该降频。
  • Expires 比 Date 早一秒：Date 是 15:22:35，Expires 是 15:22:34。这不是时钟漂移，是刻意的——配合 Cache-Control: no-cache，让任何中间层都无法把这次响应当作新鲜缓存。这条细节可以用来判断"这个响应是不是被 CDN 缓存过"。
  • X-Cache-Webcdn：BYPASS from blzone05 表示请求没走缓存、直穿到源站，blzone05 是接入层节点名。如果出现 HIT，说明拿到了缓存副本，数据可能滞后。
  • Access-Control-Expose-Headers：只暴露了 X-Cache-Webcdn。浏览器里读不到 Bili-Status-Code，这也是为什么前端只能靠响应体的 code。

三条经验：

3.4 弹幕接口的头与体

弹幕 protobuf 接口是少见的"返回二进制"的接口，行为跟 JSON 接口不同：


curl -sS -o /dev/null -w '%{http_code} %{content_type} %{size_download}\n' \
  -H 'User-Agent: Mozilla/5.0 ... Edg/140.0.0.0' -H 'Referer: https://www.bilibili.com/' \
  'https://api.bilibili.com/x/v2/dm/web/seg.so?type=1&oid=170001&pid=1&segment_index=1'


200 application/octet-stream 303

Content-Type 是 application/octet-stream，code 不在头里（Bili-Status-Code 也不出现），错误只能靠 HTTP 状态码和响应体长度判断：正常分片至少几百字节，如果返回 200 但只有几十字节，多半是参数错（oid 传了 avid 而不是 cid）。这一点跟 JSON 接口的"永远 200"完全相反，写客户端时要分开处理。

5. 工具链现状

5.1 仓库自带的东西

SocialSisterYi/bilibili-API-collect 本身不是一个 SDK，它只提供三类"半成品"：

| 内容 | 位置 | 覆盖到哪 | | --- | --- | --- | | 接口文档 | docs/**/*.md | 557 条可用接口，含参数表、响应字段表、curl 示例。没有机器可读的规格，只有人看的表格 | | gRPC 定义 | proto/bilibili/、proto/pgc/、proto/datacenter/** | APP 端全部 gRPC 消息体。proto/bilibili 下有 account、ad、app、broadcast、cheese、community、creative_tool、dagw、dynamic、gaia、im、live、main、mall、metadata、pangu、pgc、polymer、relation、rpc、vas、vega 二十余个包 | | gRPC 接入说明 | grpc_api/readme.md | 主机（grpc.biliapi.net 原生 / app.bilibili.com Failover）、identify_v1 {access_key} 鉴权、九类 x-bili-* Metadata 的构造要求 |

proto/ 里的东西是逆向官方粉版 APP 得来的，文档原话是"一般不会有错误，但是可能有更新"，并建议"有实际应用需求的自行反编译 APP，定位到 com.bapis.* 自行补足"。所以它适合当参考实现，不适合当稳定 SDK。

gRPC Metadata 是这套东西里最容易被低估的部分：除了 authorization，还必须带 x-bili-fawkes-req-bin、x-bili-metadata-bin、x-bili-device-bin、x-bili-network-bin、x-bili-restriction-bin、x-bili-locale-bin、x-bili-exps-bin 七个二进制头，以及 x-bili-aurora-eid、x-bili-trace-id、buvid 三个 ASCII 头。少一个就被判非法客户端，且报错信息不会告诉你少了哪个。这也是为什么社区里直接用 gRPC 的项目很少——门槛全在元数据组装上。

5.2 常用第三方

| 项目 | 语言 | 覆盖范围 | 一句话评价 | | --- | --- | --- | --- | | bilibili-api（Nemo2011） | Python | 视频、用户、动态、直播、专栏、音频、番剧、搜索结果、登录（含扫码/密码/短信）、wbi 签名、凭证刷新 | 覆盖最全的一站式封装，把 wbi、buvid、csrf 都包进去了；缺点是版本迭代快、接口名常变，且部分模块依赖 aiohttp | | biliup | Python/Go（含 Rust 组件） | 投稿上传、直播录制、弹幕录制 | 强项在"写"和"录"，不是读接口；直播录制是它最成熟的功能 | | you-get | Python | 视频/番剧/音频下载，支持 DASH 合流 | 单文件下载够用，取流逻辑老，遇到新清晰度（AV1、HDR）支持滞后 | | yt-dlp | Python | BiliBili extractor + BiliBiliBangumi + BiliLive 三个 extractor，支持 DASH、字幕、弹幕（--write-subs / danmaku 转换） | 目前维护最勤的通用下载器，B 站部分对大会员清晰度与地区限制处理得最好；不适合当 API 客户端用 |
