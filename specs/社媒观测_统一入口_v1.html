社媒观测：一个观测面，不是五个客户端

日期：2026-11-23 状态：设计 + 第一版实现（bilibili、douyin 已跑通）

一、命题

要做的东西不是"每个平台一个抓取脚本"，是一个观测面：同一组动作、同一种返回形状，覆盖所有平台。

理由：抓取代码是一次性的，观测面是可累积的。前者每加一个平台就多一份要维护的东西，后者每加一个平台只多一个 adapter。

二、只做四个动作

| 动作 | 语义 | 参数 | | --- | --- | --- | | hot | 平台此刻在推什么（榜单前 N） | platform, n | | search | 按关键词找内容 | platform, q, n | | item | 单条内容的结构（作者、时间、互动数、正文） | platform, url_or_id | | text | 单条内容的文字（字幕优先，识别兜底） | platform, url |

不做动作面：不发帖、不点赞、不评论、不批量私信。理由是观测面出错只是数据难看，动作面出错是账号没了。

三、平台之间真正能对齐的不是接口，是单位

  • hot 对齐的是"平台自己的排序"，不是我重新排的。各平台算法不同，重排会把这个差异抹掉，而差异本身是信息。
  • search 对齐的是"平台自己的相关度"，同理。
  • item 对齐的是字段名，不是字段含义（bilibili 的"播放"和 douyin 的"点赞"不可比，所以只归一化名字，不归一化数值）。
  • text 是唯一能完全对齐的：都是文字。

四、三层分裂与解法

一、鉴权分裂。 四种： 1. 公开接口（bilibili 的 x/web-interface/popular）——直接 fetch。 2. 登录态 cookie（bilibili 字幕列表）——.tmp/bili.cookie。 3. 浏览器会话（douyin）——.tmp/edge-profile + CDP，签名由页面自己算。 4. 请求签名（小红书 x-s、微博部分接口）——最贵，要么逆向，要么走 3。

原则：能用 3 就不用 4。浏览器会话这条路一次投入，所有"签名算不出来"的平台都能覆盖，因为它借的是人家自己的前端。

二、形状分裂。 时长有 "06:31" 和秒数两种；点赞有 "1.9万" 和整数两种；正文有的带标签有的不带。全部在归一化层处理，adapter 只管原样取。

三、稳定性分裂。 接口会变、会限流、会加验证码。所以每个 adapter 必须能回答"这次失败断在哪一层"：会话过期 / 签名不对 / 接口改了 / 被拦。

五、架构


会话层    .tmp/bili.cookie（bilibili） · .tmp/edge-profile + CDP（douyin、以后的小红书/微博）
取数层    adapters/<platform>.mjs   每个只做 hot / search / item / text
归一化层  { platform, rank|id, title, author, url, extra{} }
出口层    CLI（tools/social/probe.mjs）+ MCP server（待做）

出口为什么选 MCP：工具名固定、参数少、返回 JSON，我每次不用重写抓取代码，直接调工具。这也解释了为什么之前 84 个 westock 工具用起来很顺——形状固定。

六、平台矩阵

| 平台 | 榜单 | 搜索 | 单条 | 文字 | 主要障碍 | | --- | --- | --- | --- | --- | --- | | bilibili | 公开接口 ✓ | 公开接口 ✓ | 公开接口 ✓ | 登录态字幕 ✓ / whisper 兜底 | 无 | | douyin | CDP ✓ | CDP | CDP ✓ | 无字幕接口，只能下载+识别 | MSE（blob 地址），要从网络请求挑流 | | weibo | 热搜有接口，需探 | 需 cookie | 需 cookie | 无字幕概念 | 登录态 | | xiaohongshu | CDP | CDP | CDP | 无 | x-s 签名，只能靠浏览器 | | twitter/X | 需 cookie | 需 cookie | 需 cookie | 无 | 登录态 + 反爬 |

七、"社区整体状态"不是榜单，是变化量

榜单每天都长得差不多，单看没有信息。真正有用的是差异：

  • 今天新进榜的（前 50 里昨天没有的）
  • 连续在榜的（说明是结构性话题，不是热点）
  • 掉出榜的（说明热度已过）
  • 跨平台同时在推的（真·社会性事件 vs 平台自己的运营）

所以第二天起要存快照：.data/social/YYYY-MM-DD/<platform>.json，然后算集合差。这一步才是"看社区整体情况"，前面都只是取数。

八、判据

一个版本算成的标准：

1. node tools/social/probe.mjs <platform> --n 10 在 60 秒内给 10 条，字段齐（title/author/url 非空）。 2. 同一条内容连跑两次，url 相同（说明 id 稳定，不是每次新生成）。 3. 失败时输出能指出断在哪层（会话/签名/接口/被拦），不是一句 "fetch failed"。 4. 加一个新平台，只新增一个 adapter 文件，不改归一化层与出口层。

九、分步

1. 已完成：tools/social/probe.mjs，bilibili（公开接口）+ douyin（CDP）两个 adapter，统一输出。 2. 下一步：包成 MCP server（四个工具名 social_hot / social_search / social_item / social_text），text 直接复用 tools/media/v2t.py。 3. 再下一步：加 xiaohongshu（CDP 路线，跟 douyin 共用会话层）、weibo（先探接口）。 4. 最后：每日快照 + 差异报告，接进 rabot 语料。

十、不做什么

  • 不做统一登录：每个平台各存各的会话，不试图做"一个账号通吃"。
  • 不做全量抓取：只要前 N，够看趋势。
  • 不做互动：见第二节。
  • 不追求字段语义可比：跨平台比较只在"有没有""涨没涨"这一层做，数值本身不并表。

十一、三家真实请求/响应头（2026-11-23 抓的）

bilibili：鉴权在 Cookie，头里只有"礼貌"

请求（x/web-interface/popular）：


GET /x/web-interface/popular?ps=5&pn=1
User-Agent: Mozilla/5.0
Referer: https://www.bilibili.com/

响应：


Bili-Status-Code: 0                  ← 业务码独立于 HTTP 码
Bili-Trace-Id / X-Bili-Trace-Id      ← 双 trace，网关与后端各一段
X-Rid-Result: 2                      ← 风控结论（2=放行）
X-Ticket-Status: 1
Cpu_usage: 71                        ← 后端把自身负载也发出来
X-Bili-Metadata-Ip-Region: CN
X-Cache-Webcdn: BYPASS from blzone05 ← 自建 CDN 的缓存决策
Expires: ...00:15:30Z                ← 比 Date 早一秒，故意的
Cache-Control: no-cache

x/player/wbi/v2 多一个 Set-Cookie: sid=...，接口名带 wbi 但不校验签名（实测不带 w_rid 也 200）。

douyin：签名在 query，设备指纹也是签名输入

请求（/aweme/v1/web/multicast/query/），头只有四个：


uifid: c8ccd135…（256 位十六进制，设备/用户指纹）
Referer: https://www.douyin.com/hot
User-Agent: Mozilla/5.0 … Chrome/131.0.0.0
Accept: application/json, text/plain, */*

真正的东西全在 query：a_bogus（签名，每次不同）、msToken、verifyFp/fp、webid、uifid，外加一长串环境参数（screen_width、screen_height、device_memory、downlink、effective_type、round_trip_time、pc_libra_divert…）。它把"运行环境"当成签名的一部分。

响应：


x-tt-trace-id / x-tt-logid / x-tt-trace-host   ← 三层 trace
x-tt-trace-tag: id=26;cdn-cache=miss;type=dyn
x-janus-info: MM22hes81…                       ← 网关侧加密载荷
bd-tt-error-code: 0
status_code: 0                                 ← body 里再来一份业务码
cookie_ttwidinfo_webid: 7701097945345574451    ← 服务端把设备 id 塞回客户端
server-timing: cdn-cache;desc=MISS, edge;dur=2, origin;dur=62
via: CHN-JSyangzhou-CMCC18-CACHE21[64],…       ← 多级 CDN 路径
server: TLB

weibo：不签名，直接给

请求：只有 User-Agent + Referer: https://weibo.com/。 响应（ajax/side/hotSearch，匿名 200，52 条）：


set-cookie: XSRF-TOKEN=…; path=/; secure
PROC_NODE: weibopro-node-web-696b4995c5-9btf7   ← 内网节点名直接暴露
Lb: 2409:8c00:7821:2303::56
Ssl_node: mapi-10-54-7-26.hj4.intra.weibo.cn    ← 内网 IP 也在
x-readtime: 16
x-frame-options / x-xss-protection / x-content-type-options
Server: SHANHAI-SERVER

三家对比，一句话各一条

| | 鉴权位置 | 签名 | 业务码 | 反爬手段 | | --- | --- | --- | --- | --- | | bilibili | Cookie（SESSDATA） | 名义有 wbi，实测不校验 | Bili-Status-Code | 风控头 X-Rid-Result，弱 | | douyin | query 里的 a_bogus + 指纹 | 必需，前端 JS 现算 | status_code | 环境指纹进签名，强 | | weibo | 无 | 无 | ok | 几乎无，靠登录态管读以外的动作 |

结论：三家都不是"在 header 里验 token"的设计，而是三种完全不同的鉴权姿势。 所以统一入口不能在 header 层做抽象，只能在 adapter 层做——这也是第十二节契约存在的原因。

十二、加平台的契约（扩展点）

新增一个平台 = 新增 tools/social/adapters/<name>.mjs，导出：


export const meta = {
  name: 'xiaohongshu',
  auth: 'browser',        // none | cookie | signature | browser
  needs: ['edge-profile'],// 声明依赖，缺了就直接报这一层断了
  actions: ['hot', 'search', 'item', 'text'],
};
export async function hot(n) { /* → 归一化数组 */ }
export async function search(q, n) {}
export async function item(url) {}
export async function text(url) {}

约束三条： 1. 返回形状不许改，只能在 extra 里加字段。 2. 不许在 adapter 里做跨平台判断（谁新谁旧、谁热谁冷），那是上层的事。 3. 失败必须抛带层的错误：new Error('auth: 会话过期') / 'sign: a_bogus 算不出' / 'api: 接口改了' / 'block: 被拦'。

按这个契约，小红书与 X 都走 auth: 'browser'，复用同一个 CDP 会话层，各自只写取数逻辑。

十三、视频平台：腾讯视频 / 爱奇艺 / YouTube（2026-11-23 抓的）

爱奇艺：配额头写得最明白

真接口是 mesh.if.iqiyi.com 网关，路径全在 /portal/lw/...、/portal/pcw/...：


GET /portal/lw/search/keywords/hotList?device_id=…&v=17.113.27034&appMode=&src=
GET /portal/pcw/abtest?deviceId=…&version=1.0.0.1
GET /portal/pcw/weather/data?version=1.0.0.1

响应头（这几条是它最讲究的地方）：


x-ratelimit-limit-1: 20000        ← 配额上限
x-ratelimit-remaining-1: 169      ← 还剩多少
x-ratelimit-reset-1: 0
x-envoy-upstream-service-time: 25 ← 走 Envoy
x-trace-id: 14a6d9d5b3224084…
access-control-allow-origin: *    ← CORS 直接放开
access-control-expose-headers: *
server: Skywalker/3.10.1/34156    ← 网关代号

另一条 pcw-api.iqiyi.com（3000 配额）响应头里还声明支持 x-b3-traceid/x-b3-spanid——Zipkin 那套 B3 头，说明它内部是标准链路追踪。

设计特征：把"你能调多少次"当成协议的一部分（配额头 + 429 语义），客户端可以据此自己降速。 这是四家里唯一这么干的。

腾讯视频：trpc 路径 + 老式协议体


GET https://pbaccess.video.qq.com/trpc.universal_backend_service.hot_word_info.HttpHotWordRecall/GetHotWords
      ?appID=3172&appKey=lGhFIPeD3HsO9xEp&platform=2&channelID=0&v=2992322
→ {"data":{"errorCode":0,"hotWordList":[{"searchWord":"斗破苍穹剧场版 双帝之战","itemParams":{"cid":"mzc00200u6gslvo"}}…]}}
  • 路径形态是 trpc 风格：/trpc.<包>.<服务>.<方法>/<方法>，一个 URL 里服务名和 HTTP 方法名各出现一次。
  • 鉴权是最弱的一种：appID=3172&appKey=lGhFIPeD3HsO9xEp 明文写在 query 里——这个 key 是从页面源码抄的，等于公开。
  • 老式协议体：{"ret":0,"msg":""}（getPage 那类接口就是这样，ret 非 0 才有 msg），新接口换成 {"data":{"errorCode":0}}，两套并存。
  • 响应头把链路信息全放出来：x-client-ip、x-server-ip、x-upstream-ip、x-nws-log-uuid、x-cache-lookup: Cache Miss，配 age/expires 做 60 秒缓存。

设计特征：方法名进 URL、appKey 进 query——鉴权等于没有，防的是"别人乱调"，不是"别人知道"。

YouTube：整站不可达

实测 www.youtube.com、m.youtube.com、youtube-nocookie.com、youtubei.googleapis.com 全部 status=000（超时/重置）；inv.nadeko.net、yewtu.be、pipedapi.kavin.rocks 三个镜像也是 000。

结论：不是 API 问题，是出口网络到 Google 系整段不通。所以在 probe.mjs 里它只能是 auth: 'proxy' 一档——要么挂 HTTP 代理（HTTPS_PROXY 或 adapter 里 dispatcher 指代理），要么走浏览器（同样不通）。错误必须抛 block: 出口不通，不许伪装成"接口改了"。

官方 API 的形状（未验证，仅台账）：https://www.googleapis.com/youtube/v3/videos?chart=mostPopular&regionCode=CN&part=snippet,statistics&key=API_KEY，需要 API key 与配额（每天 10,000 单位，一次 list 花 1 单位）。
