四、有效性的两个真问题

4.1 取证权在被审者手里

judgeEvidence 的越界判定（store.js:185-193）只看 evidence 里自报 type:"file" 的 ref 前缀。 不填 file 证据 → 一条都不越界。同理 M02 判「声称测试通过」只看 claim 里有没有「测试/通过」字样与 evidence 里有没有 test 类型。

这不是规则写错，是结构问题：被审者同时是取证者。 规范 §11.1 说「校验器质量封顶一切」，实际更糟一层——校验器的输入由被审者提供，质量封顶之外还加了一道自愿性。

修法（可自动）：declare 时记工作区快照（路径+size+mtime），verify 时 diff 出真实改动集合，与 allowPaths 比对。不依赖自报。

4.2 没有强制入口

M01–M04、P01 全部依赖 task 存在。不 declare 直接干活 → 记账层整体失效，gate_verify 仍然返回 PASS（task 为 null 时只走「有无证据」分支）。 gate_check 也不看有没有 task。

也就是说：只要不登记，整套约束自动失效，且没有任何提示。 这与 §0「无自我豁免条款」直接冲突——工具给了 agent 一个静默豁免通道。

修法：gate_verify 在无 open task 时 VETO；gate_check 在无 task 时 WARN「这次检查没有任务边界」。

五、修复清单

P0（不修，规范等于自愿遵守）

1. 强制入口：无 open task 时 gate_verify VETO、gate_check WARN。 2. 真实改动集合：declare 存快照，verify diff 比对 allowPaths，不再依赖自报证据。 3. 验收条件变更留痕：declare 时 acceptance 与旧值不同 → 写 .gate/task-history.jsonl，要求 reason，否则 WARN。 4. 过程预期字段：declare 加 expect（一句话：改完预期哪个测试通过/什么行为变化），verify 时核对「中/未中」。

P1（影响日常判定）

5. T04 扩：自反比较 x === x、a).toBe(a、恒真不等式、toBeTruthy(true)、assertTrue(true)。 6. E01 扩：return null/false、.catch(() => {})、同行 except: pass、except: continue、catch 内只有 log。 7. H01 扩：变量名含 key/token/secret/cred + 高熵串；AWS AKIA、GitHub ghp_、Slack xox 前缀；.env 文件纳入扫描。 8. D01 修：同时试「相对 root」与「相对工作区根」，修掉子目录扫描误跳过。 9. I-5.7 双验证结构化：evidence 加 phase: "fail-before" | "pass-after"，改测试时必须两条，缺一条 VETO。 10. WORK_STATE 新鲜度：存在但 >14 天未更新 → INFO；未存在且 level ≥ L3 → WARN。

P2（长期）

11. 指标计算：从 evidence.jsonl 算越界率、无证据率、空转率、证据完整率（§10）。 12. 真变异测试（v1.0 §6.2）：对 JS/Python 做等价变异，跑测试看是否红；这是唯一能给「校验器质量」定量的手段。 13. 结构一致性轻量版（I-3 唯一可自动化的部分）：循环依赖、跨模块深路径 import、重复代码块哈希。 14. 并行方案登记（v1.0 §7）：同一目标下多个方案各自攒证据，超限淘汰。
