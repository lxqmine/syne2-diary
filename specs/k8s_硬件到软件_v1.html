k8s 从硬件到软件：一条链走到底

一句话：k8s 不碰硬件。 它只维护一份"期望状态"，真正碰硬件的是三层——设备驱动、容器运行时、CNI/CSI。
所以"k8s 怎么和硬件协同"这个问题，答案不在 k8s 里，在它下面那三层，以及它和那三层之间的几个交接点上。

---

〇、整条链，七个交接点


硬件（CPU/内存/网卡/盘/GPU）
  ↓ ① UEFI/ACPI → 内核 → 驱动 → udev        ← 设备"出现"
内核抽象（cgroup v2 / namespace / NUMA / /dev）
  ↓ ② kubelet 采集 Capacity，扣掉 reserved 得 Allocatable   ← 资源"记账"
调度（scheduler 只看 Allocatable，看不见 NUMA 与型号）
  ↓ ③ 调度结果写进 Pod.spec.nodeName                        ← 请求"落地"
kubelet → CRI → containerd → runc
  ↓ ④ runc 创建 namespace + cgroup，绑核/绑 NUMA             ← 资源"真分配"
容器进程
  ↓ ⑤ CNI 建 veth、配路由、下发 eBPF/iptables                ← 网络"接通"
  ↓ ⑥ CSI attach/mount（云盘/本地盘/NVMe）                   ← 存储"挂上"
  ↓ ⑦ 中断亲和、RPS/RFS、C-state、频率                       ← 性能"最后一公里"

七个交接点，每一个都能单独坏，而且坏的样子不一样。

---

一、① 硬件出现：UEFI → 内核 → 驱动

| 环节 | 干了什么 | 坏了会看见 | |---|---|---| | UEFI/ACPI | 把设备树/PCIe 拓扑交给内核 | dmesg 里设备缺失、lspci 看不到 | | 内核模块 | 加载驱动（mlx5_core、nvme、i40e） | dmesg 报 probe failed | | udev | 建 /dev 节点、改权限、起命名规则 | 设备在但容器里看不到（device plugin 的活） | | 固件 | 网卡/RAID/NVMe 的微码 | 随机丢包、掉盘，重启就好 |

锚点：当我看到"宿主机 lspci 有、容器里没有"，先查 device plugin 与 udev 规则，因为 k8s 只认上报上来的资源名。

---

二、② 资源记账：Capacity 与 Allocatable 不是一回事


Allocatable = Capacity − kube-reserved − system-reserved − eviction-threshold

一台 64C/256G 的机器，Allocatable 常常是 60C/230G。这中间的差，是给 kubelet、容器运行时、内核、以及驱逐阈值留的。


kubectl describe node <n> | grep -A5 Allocatable

这一层最常见的误解：以为"节点 256G，就能跑 256G 的 Pod"。调度器只信 Allocatable，超了就是 Pending，而 Pending 的原因写在 Events 里，不写在指标里。

锚点：当我看到 Pod 一直 Pending 而节点看起来"很空"，先看 Allocatable 与 Requests 的和，因为调度器算的是账，不是实际用量。

---

三、③ 调度：它看不见硬件，只看得见"被上报的资源名"

调度器做的事只有三步：过滤（谁能放）、打分（放哪更好）、绑定（写 nodeName）。

它不知道：

  • 这块 GPU 是 A100 还是 4090（只知道 nvidia.com/gpu: 1）
  • 这个 NUMA 节点上还剩多少内存（除非 Topology Manager 给了 hint）
  • 这台机器的网卡是 10G 还是 25G（除非打了 label）

所以硬件信息进 k8s 的方式只有三种：resource 名（device plugin 上报）、label（人打的）、annotation（人写的）。

锚点：当我看到两个 Pod 被调到同一张卡或跨了 NUMA，先看 Topology Manager 的策略与 device plugin 的上报粒度，因为调度器没有硬件拓扑这个概念，只有"资源够不够"。

---

四、④ 真分配：runc 那一下

kubelet 把 Pod 交给 CRI，containerd 拉起 runc，runc 做四件事：

1. clone 出新进程（新 PID namespace） 2. 挂载（overlayfs 叠镜像层 + 卷） 3. 写 cgroup v2：cpu.max、memory.max、io.max、cpuset.cpus 4. execve 进容器

CPU 绑核就发生在第 3 步：cpuManagerPolicy: static 时，保证型 Pod 会拿到独占的 cpuset.cpus，其余用共享池。不配就是共享，共享就是抢。

锚点：当我看到"CPU 没用满但延迟抖"，先看 cpuset.cpus 与 cpu.max 的配额，因为配额是把双刃剑——它限流，也让你在 throttle 周期里排队。

---

五、⑤ 网络：CNI 是硬件与 k8s 之间最薄的一层


Pod eth0 ← veth pair → 宿主机 vethX → 路由/网桥/eBPF → 物理网卡 → 交换机

| 硬件相关项 | 为什么重要 | |---|---| | MTU | Pod 网络的 MTU 必须 ≤ 物理 MTU − 封装开销（VXLAN 减 50） | | offload（TSO/GSO/checksum） | 开了快，但 overlay 下可能算出错包 | | RSS 多队列 | 单队列 = 一个 CPU 扛所有软中断 | | SR-IOV | 绕过内核直接给 Pod 一个 VF，延迟低但热迁移没了 |

锚点：当我看到"小包正常、大包超时"，先量 Pod 网络的 MTU，因为 VXLAN 减 50 之后，1500 的包会被静默丢弃。

---

六、⑥ 存储：attach 与 mount 是两件事


CSI Controller：attach（云盘挂到节点）→ CSI Node：mount（挂到容器）

分开记的原因：attach 失败和 mount 失败，看到的完全是两种现象。attach 失败是"卷不在这个节点上"，mount 失败是"卷在但挂不上"（文件系统、权限、只读）。

锚点：当我看到 Pod 卡在 ContainerCreating，先看 CSI 的 Events 与 PV 的 nodeAffinity，因为跨可用区的卷永远 attach 不上。

---

七、⑦ 最后一公里：中断与电源

这一层 k8s 完全不管，但它决定了"配置全对，性能不对"。

| 项 | 现象 | |---|---| | IRQ 全打到 CPU0 | 一个核 100%，其余闲 | | RPS/RFS 没开 | 单队列网卡软中断瓶颈 | | C-state 太深 | 延迟毛刺，p99 突然跳 | | 频率调节器 powersave | 吞吐上不去，频率上不来 |

锚点：当我看到"CPU 总利用率不高但 p99 很差"，先看 /proc/interrupts 的分布，因为队列和中断不均衡时，平均值会骗人。

---

八、五个真问题（比背流程有用）

1. Allocatable 比物理少 —— 用户以为节点空，调度器以为满。 2. NUMA 跨节点 —— 内存分配在另一个 socket，延迟翻倍，指标上看不出来。 3. 中断不均衡 —— 平均值正常，p99 崩。 4. MTU 与封装 —— 小包通、大包死，最像"网络不稳"。 5. device plugin 不代表拓扑 —— 上报"有 8 张卡"，不代表这 8 张卡在同一个 NUMA 上。

九、和前面那份 OSI 拓扑的关系

链路_OSI拓扑_v1.md 走的是一台机器出网的链（七层、五个交接点）。 这份走的是一个 Pod 落地的链（硬件、记账、调度、创建、网络、存储、性能；七个交接点）。

两份的判据是同一条：拿掉它，系统是散了还是只是变慢了——网络断了是散，NUMA 错了是慢。散的优先修，慢的排后面。

---

十、补：GPU 这一段为什么最密

前面说"要往下钻先钻 GPU"，理由是它把三件事挤在了一起：资源名、拓扑、驱动版本。三样里任何一样错，现象都是"跑不起来"，但修法完全不同。

10.1 资源名有四种，别混

| 资源名 | 含义 | 坑 | |---|---|---| | nvidia.com/gpu: 1 | 整卡 | 默认是时间片共享，两个 Pod 同卡会互踩显存 | | nvidia.com/mig-3g.20gb | MIG 切片 | 切了 MIG 就不能整卡用，重配要重启节点上的 GPU | | nvidia.com/gpumem | 显存（部分发行版） | 不是 k8s 原生，靠 device plugin 自己实现 | | rdma/rdma_shared_device_a | IB 设备 | 要给 IPC_LOCK + hostNetwork，不然 RDMA 起不来 |

锚点：当我看到两个 Pod 都在跑却互相 OOM，先看它们是不是共享同一张卡的时间片，因为 nvidia.com/gpu 默认不做显存隔离。

10.2 device plugin 报的是数量，不是拓扑

kubelet 从 device plugin 拿到的只有"有几个、健康不健康"；NUMA 亲和要靠 device plugin API 的 TopologyInfo 字段 + kubelet 的 Topology Manager 策略（single-numa-node / restricted / best-effort）。

不上报 NUMA，调度器就以为 8 张卡是均质的。实际可能是 4+4 分在两个 socket 上，跨 socket 访问显存延迟翻倍。

锚点：当我看到"卡够、跑得慢、nvidia-smi 正常"，先看进程的 NUMA 亲和与 nvidia-smi topo -m，因为跨 NUMA 的显存访问在指标上只表现为"慢"。

10.3 驱动有三层，版本必须一层层对


内核模块 nvidia.ko / nvidia-uvm / nvidia-peermem
   ↓ 用户态 libcuda.so（驱动版本，如 550.54）
   ↓ 容器里的 CUDA runtime（如 12.4）
   ↓ 框架（torch 编译时对着某个 CUDA 版本）

nvidia-container-toolkit 在容器启动时把宿主机的驱动库挂进去。所以容器里不该装驱动，只装 CUDA runtime。

版本错配的三种现象，长得完全不一样：

  • 容器里 nvidia-smi 有输出、torch 说 no CUDA device → 挂载了驱动但没挂 device 节点，或 NVIDIA_VISIBLE_DEVICES 没设
  • CUDA error: unknown error → 用户态驱动与内核模块版本不符（升级内核后没重启）
  • 一跑就 out of memory 但显存空着 → 碎片或 MIG 切片的显存上限

锚点：当我看到"nvidia-smi 正常但框架说没卡"，先看容器里的 /dev/nvidia* 与 NVIDIA_VISIBLE_DEVICES，因为 toolkit 挂的是库，设备节点是另一件事。

10.4 GPUDirect 与 IB：这一段几乎全是硬件

要让 GPU 直接读网卡（RDMA），需要：ib_core + nvidia-peermem 加载、容器 privileged 或至少 IPC_LOCK + NET_ADMIN、hostNetwork、MTU 对齐（IB 常见 4092）、PFC 无损队列配好。

少一样，现象是"能跑但带宽只有十分之一"，或者干脆 hang 在 ibv_reg_mr。

锚点：当我看到 RDMA 带宽只有零头，先看 ibv_devinfo 的 MTU 与 nvidia-smi topo -m 里 GPU 到网卡的路径（走 PCIe switch 还是跨 socket），因为这两样决定了上限，代码决定不了。
