诊断：workbuddy 与「老是让我重启」

2026-11-21。取证脚本 tools/diag/workbuddy-restart.test.mjs。

一、结论先说

两件事其实是同一件事。

1. workbuddy 没装坏。 dsh-connect-workbuddy@5.20.2 在 profile 里 enabled、installed，行 include:dsh-connect-workbuddy 在，native/turing-sdk 在。 2. 坏的是"更新它"这条路。 操作日志 92 条，applied 0 次。每次更新都走同一条死路：装 → 失败（already-installed）→ 卸 → 失败（bundle-in-use / operation-error）。一步也没换成。 3. 重启提示是这条死路的回声，不是 bug。 宿主的规定写死：换掉一个已装包必须重启才能加载新的模块代（restart-required，reason host-module）。workbuddy 带原生目录，正属此类。所以"要重启"永远正确——只是因为前面那步没成功，重启完还是旧的，下次再提示。

一句话：不是它在重启，是它从来没成功过一次，所以永远在等重启。

二、证据

C:\Users\admin\AppData\Roaming\dsh-desktop\plugin-operations\operations.jsonl（92 条）：

| 项 | 数 | |---|---| | 生效 applied | 0 | | already-installed | 22 | | operation-error | 19 | | bundle-in-use | 5 | | 「装失败→两步后卸失败」空转对 | 22 |

只有两组 run：2026-11-20 14:41、2026-11-21 12:08。每组都是一口气对十几个已装包挨个做一遍。

进程侧：electron.exe 24204；harness host 12324 监听 127.0.0.1:55791，hostStartedAt 2026-11-21T12:09:46Z —— 正好是他那轮操作之后重启的那一次。也就是说重启是真发生了的，只是重启没能救回一次失败的更新。

三、为什么必然失败

宿主的更新流程是"先装新的，再把旧的摘掉"。对已安装且正在运行的包，这两步都过不去：

  • 装新的：目标已存在 → already-installed。
  • 摘旧的：包正在被宿主加载 → bundle-in-use；或者文件被占用/目录被旁路 → operation-error。

两个错都不是"暂时性故障"，重试不会变。所以循环稳定复现，每次都以"需要重启"收尾。

三点五、动手前先查了这一下（结论：不用动）

.generations/ 里的账：desired.json 12 条，live/ 12 条，逐字相同；staging/、trash/ 都空。

意思是没有任何待生效的改动。既然没有待装的版本，"停用→重启→装"跑下去是空转——装的是已经在跑的那个版本，第一步还是 already-installed。

所以那个重启提示不是任务，是墓碑：它记着一次从来没成功的替换。

四、能做的三件事

1. 别用"全部更新"。 这是触发源。要更哪个包，单独更。 2. 正确次序：停用 bundle（set_bundle enabled:false）→ 重启一次 → 安装新版本 → 再重启一次。停用之后包不再被加载，摘旧那步才不会撞 bundle-in-use。 3. 绕过插件管理器：host 停着的时候直接换 profiles/web/node_modules/<包名> 目录，再启动。适合自己有包、只想换文件的情况。

五、顺手查到的另一处

启动日志里有：


launch requested (safe mode)
safe mode: third-party web profile bundles are blocked
warn patch: entry "redteam-mode-store" not found
warn patch: entry "redteam-mode-ui" not found

dsh-purge-community 的 overrides 里点名了 redteam-store、redteam-ui、redteam-mode、redteam-mode-store、redteam-mode-ui 五个条目，而这五个在 profile 里不存在。启动时找不到就 warn，本身不致命；但它一旦让宿主判定"补丁层坏了"，就会进安全模式，进安全模式的表现之一就是叫你再启动一次。这条与上面的更新死路是两个独立来源，都会长成"重启"。
