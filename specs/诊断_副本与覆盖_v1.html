诊断：改了没生效（副本与覆盖）

一句话："我改了但没生效"，先数这个值有几个副本；副本过一，是结构问题，不是手误。

一、为什么单写一条"要仔细"没用

因为这毛病长得不像粗心。改动是对的、命令是成功的、文件里也确实写进去了，但运行的那份不是它。人在这种时候会去怀疑缓存、怀疑网络、怀疑权限，唯独不怀疑"这个值不止一份"。

所以要有一条不靠自觉的检查：动手之前问一句"这个值现在住在哪几个地方"。

二、三种形态（都在这台机器上真发生过）

2.1 回写覆盖：你改完，另一个写者按内存快照写回去

  • 现场：harness/profiles/desktop/package.json 的 bundles 数组。用 edit 加了一行，桌面端退出时整份文件按内存状态重写，那行消失；dependencies 那行却留着（因为它本来就在内存里）。
  • 判据：改动立刻生效、重启后消失，就是这一类。
  • 修法：跟着最后一个写者改。plugin_manager set_bundle 之所以能留住，是因为它跟桌面端走同一个写入通道；edit 是绕过它直接改盘。

2.2 空值冲默认：默认值不是"没传"，是"被传了空值"

  • 现场：plugins/dsh-social/smoke-all.mjs 第一版把素材池的所有字段灌给每条 endpoint，把 spec 自己的默认值（type、sort）冲成空串，于是所有评论请求回 -400。
  • 判据：参数看着齐全，接口却报参数错，先打印最终发出的 query/body，跟 spec 默认值逐字比。
  • 修法：以 spec 默认值为底，只把空串占位换成真值；空值不许穿过默认层。

2.3 半份配置：抄了 token，漏了同一个响应里的 baseurl

  • 现场：微信 iLink 的凭据。配对成功时服务端同时返回 bot_token 与 baseurl，我手写凭据文件只抄了 token，于是每次拉消息都 -14 session timeout，看起来像 token 过期（其实 token 没过期机制）。
  • 判据：报"过期/未授权"，但 token 明明有效，就是同一个响应里还有别的必需字段没落。
  • 修法：配对/授权的返回值整份落盘，不许手挑字段。

三、检查顺序（照这个顺序，别跳）

1. 数副本：grep -rl "<值或键名>" 全盘搜，含配置文件、缓存、环境变量、启动脚本。 2. 找最后一个写者：谁在退出/启动/定时时写这个文件。桌面端、守护进程、安装器都算。 3. 看生效判据：能不能在运行时读出这个值（/status 之类），读不出来就加一个读数。 4. 只有前三步都对上之后，才允许怀疑缓存与权限。

四、两条硬规矩

  • 同一个值只留一份。 多份就要有同步机制；没有同步机制的多份，等于迟早有一份是旧的。（微信那条线最终就是靠删到只剩 .wx/token.json 才好。）
  • 配置决定代码是否生效的地方，必须有可观测读数。 platform.json 的 tool 少写一个字段，代码全对而工具就是不出现，且不报错——这类隐性开关必须能被一条命令读出来。
