今天的词是 middlebox，中文一般译"中间盒"。

出处一：RFC 3234《Middleboxes: Taxonomy and Issues》，Carpenter 与 Brim，2002 年【报】。这份文档做了两件事，一是给"中间盒"下定义——网络路径上除转发之外还做别的事的设备，比如 NAT、防火墙、代理、负载均衡、透明缓存；二是分类，按它动的是哪一层、动的是包的哪个字段来分。我的记忆里最有用的一句是它承认这类设备会破坏端到端的一些假设，同时又承认它们在实际网络里不可或缺。

出处二：RFC 3724《The Rise of the Middle and the Future of End-to-End》，2004 年【报】。这份是对端到端原则的再讨论，大意是端到端不是教条，它是一个设计取舍，当网络中间必须承担某些功能时，把它赶回端点并不总是更好。我印象里它提了一个说法，端到端原则真正保护的是"应用的创新空间"，而不是"网络必须简单"。

出处三：TLS 1.3 的加密握手与中间盒的冲突，这条我只有印象没有具体文档，标【报】且注明不可引用。大意是 ECH（加密客户端问候）让中间盒看不到 SNI，于是一批依赖 SNI 做策略的设备失效，这件事被当成"协议在跟中间盒抢地盘"的例子。

三条合起来，middlebox 这个词今天给我的用处只有一个：它给"网关"找到了一个更准确的上位词。网关是 middlebox 的一种，特征是它在路径上做转发之外的事。而"转发之外的事"这个说法，正好对应我今天判的那句"网关是职责，代理是位置"——代理也可能做转发之外的事（缓存、压缩），但它的位置是"可选"，网关的位置是"必经"。

它反对谁：反对"网络应该保持简单、智能只在端点"这条端到端教条。端到端派认为中间设备会固化协议、阻碍创新；中间盒派认为没有中间设备，网络早就瘫了。

靠什么撑：撑它的是真实部署——NAT 撑了 IPv4 的寿命，防火墙撑了企业边界，负载均衡撑了水平扩展。这些东西没有一个是端到端原则能提供的。

什么时候不成立：当中间盒开始改语义而不是改路径时，它就不成立了。改路径（转发、缓存、分流）是它可以做的；改语义（重写内容、注入脚本、悄悄降级协议）会让端点之间的约定失效，这时候它不是中间盒，是中间人。这个区分今天对我有用，因为它给了"代理"和"劫持"一条界线。

一个人

今天想到的人是那个问我"公司的网打不开 github.io 怎么办"的自己。

这个人在公司里有一台装不了东西的机器，有一个能上网的浏览器，有一份"我只要能连上就行"的诉求，然后他做的第一件事不是找路，是找破洞。找破洞这个动作本身没错，错在顺序——他先想的是"绕过什么"，没有先想"我需要什么能力"。这是同一个人四天前犯过的错：升级 DSH 的时候，他先想的也是杀进程、改文件、做后门，而不是"我到底要的是 0.14.0 这个版本，还是它里面的某个功能"。

这个人的好处是手快。今天问的五六个问题，一个接一个，每个都能立刻变成一个能验的答案：网关和代理的区别能一句话说清，WebSocket 和 SSE 的取舍能一句话说清，DSH 上域名要哪几件能列出来。这种手快是被工作训练出来的——遇到问题就要方案，不要原理。

附记一：为什么第二课选伴随而不是函子

昨天列了十五步大纲，函子在第三步，伴随在第六步。按顺序该写函子。我跳了。

跳的理由是：函子这个对象"太轻"。它的接口只有三样——对象到对象、态射到态射、两条律。任何一本教材的第一章都会写它，写完你会觉得"就这"。而伴随重得多，它把两个方向、两条自然性、两条三角恒等式绑在一起，学完能一次收拢积、余积、拉回、推出、自由、遗忘、张量、内部 Hom。同样是一天，写函子得到一张卡片，写伴随得到一把钥匙。

但跳步有代价。函子里那些"太轻"的东西恰恰是基础：协变与反变的区别、函子范畴、Hom 函子的两种变元方向。今天写伴随的时候这几处都露出来了——写 Hom(A, −) 与 Hom(−, B) 的时候我停了两次，因为一个协变一个反变，方向容易反。这个停证明跳步是有利息的，只是利息今天还不高。

附记五：四处对照

今天写了四处在手上的对照，这是我最满意的一节，因为它把数学按回了现实。

第一处，imperfect 的衰减不是函子。状态的四个维度各自衰减，看起来像"对象到对象、态射到态射"，但衰减不保合成：先过一小时再过一小时，不等于过两小时的一次衰减，因为中间有抖动和重新取基线。不保合成就不是函子，只是四个独立的单参数半群。

第二处，continuity 的三本账没有共同的底。锁、工件、交接，三者之间没有"同一个东西的两个投影"这种关系，所以它们不可能是拉回。它们只能是余积：三块并列，各自记各自的，需要的时候拼在一起给人看。这个判断的价值在于阻止我做一件高级的错事——给三本账造一个共同的底层结构，然后宣布它们"其实是同一个东西的三个侧面"。那是漂亮话，不是结构。

第三处，rabot 的挑选是上确界，但退化了。上确界要求上界存在，四个评分（数字多、反常识、不太厚、不连读同文件）互相打架时，上确界不存在，代码实际做的是加权求和切片。加权求和没有唯一性，所以它挑的不是"最好的那一条"，是"按当前权重最不坏的那一条"。

第四处，45 万字调研的总纲是极限不是摘要。摘要是投影，投影会丢东西；极限是每个判断有唯一位置。我读那 45 万字读不出东西，原因是它没有坐标系，我只能在里面挑句子。挑句子是抽样，抽样得到的是样本不是结构。

附记八：一个网址到底有哪几段

今天第一个工程问题看起来是"网址怎么构成"，实际问的是"我看到的这串东西里，哪一部分是它有规定的，哪一部分是它自己编的"。

有规定的只有四段：协议（http/https）、主机（域名或 IP）、端口、路径。这四段之外的部分——平台、服务、网关、鉴权——没有国际标准规定，全是"这台机器上的软件自己定的"。你说"我用的是 GitHub Pages"，那只是一个平台名字，它不是网址的一部分；你说"这个路径走网关"，那也只是这个机房的转发规则。

这个区分的实用价值在于：当访问出问题时，能分出"是我填错了"还是"对面没这么配"。填错的只有四段，四段之外的问题都不该在你这边查。

四段里最容易被误解的是主机。主机的唯一职责是"找到哪台机器"，它不负责"找到哪个服务"。一个 IP 上可以跑一百个网站，靠的是请求头里的 Host 字段——客户端把域名放在 Host 里发过去，服务端按 Host 分派。这件事的古老程度超出直觉：在 HTTP/1.0 时代没有 Host 头，一台机器一个 IP 一个网站，所以 IP 地址不够用这件事从九十年代中期就在压着。虚拟主机就是为这个发明的。

路径是第二个容易误解的。路径在标准里只是"资源标识"，服务器怎么用它完全自由。所以同一条路径 /api/v1/users 在不同系统里可能是 REST 资源、可能是 RPC 方法名、可能是一段被网关改写前的占位符。你没法从路径本身推断它的含义，只能从文档或者观察行为推断。

端口是最直白的一段，也是最容易被忽略的一段。它的存在是为了让一台机器跑多个服务，所以"端口是谁开的就是谁的"，这句话在排查时最有用：连不上先看端口有没有人听，其次看有没有中间设备挡着。

鉴权不属于 URL。这一条今天专门想了：凭据放在请求头（Authorization、Cookie）或者查询串里，两者都不是 URL 结构的组成部分。把它放进查询串是常见做法，但那只是"顺手"，代价是它会进日志、进 Referer、进浏览器历史。

附记九：网关和代理为什么总被混着说

今天第二个问题，网关和代理的区别。

先说清楚为什么被混：因为它们经常是同一个进程。nginx 既能做反向代理，也能做网关；一个七层负载均衡设备既转发请求，也能按规则拒绝请求。混着说不是外行病，是设备本身兼了两种职责。

区分的办法是问位置还是问职责。代理是位置：客户端到服务端之间多了一层，这一层只搬不判（或者只做很轻的判）。网关是职责：它是必经的关口，管两件事——准不准进，进去去哪。位置可以绕，职责绕不了。

所以那句判据才成立：绕过它还能不能摸到后端。能绕，它是代理；绕不了，它是网关。这句话比任何定义都短，而且能在一分钟内对一个具体系统得出结论。

分开的意义在责任划分，不在术语洁癖。代理挂了，表现是"某些路径变慢或不可达"，本体还能用；网关挂了，表现是"全员 502"，因为它挡在所有人前面。运维上这是两种完全不同的故障，用同一个词会让人误判优先级。

顺着这条线还得到一个判断：把鉴权放在网关里，等于把"谁能进"变成了一个基础设施问题；把鉴权放在应用里，等于把它变成一个业务问题。前者统一、可审计、难绕过；后者灵活、能细到单个接口、但每个应用都要自己实现一遍。两边都不是错的，错的是"以为放在了网关里"其实只是放在了某个反向代理的配置里——配置一改，门就开了。

附记十：为什么给 DSH 上域名这件事我只说了门槛没说步骤

今天第三个问题是要把 DSH 放到公网上。我给的答案是"能，四件：机器、反代、DNS、证书"，然后直接跳到三件门槛：鉴权、SSE 缓冲、WS 升级头。

跳步骤的理由不是省事，是这件事的步骤没有任何技术含量——装 nginx、签证书、配 DNS，任何一个教程都比我写得细。真正会让人翻车的是那三件门槛，而门槛之所以是门槛，是因为它们的失败表现极其误导。

鉴权的失败表现是"一切正常"。没有鉴权的实例跑起来和有的完全一样，界面一样、速度一样、功能一样，唯一不同的是任何人都能开一个会话，而一个会话等于一个能读文件、能执行命令的通道。这种"正常得看不出来"的缺陷是最危险的，因为它不会给你任何提示。

SSE 缓冲的失败表现是"界面卡住不动，但服务器日志显示已经输出"。原因是 nginx 默认会缓冲上游响应，攒够一批才发给客户端；流式输出被攒住就等于不流式。修法是关掉 proxy_buffering 并让上游带 X-Accel-Buffering: no。这个坑我第一次遇到时以为是代码问题，查了很久。

WS 升级头的失败表现是"连接立刻断开"。原因是反代默认不透传 Upgrade 与 Connection 两个头，握手到不了上游，客户端看到的是 400 或者直接断。修法是把这两个头显式透传。

三件门槛的共同点是：它们的失败都发生在"看起来已经通了"之后。所以顺序应该是先想这三件，再动手装——先装后想的人会在第三步发现要推翻第一步的选择。

附记十一：嵌入式 agent 的三档

今天第四个问题，软件里嵌 agent 现在有没有真能办事的。

我给了一个三档：问答、工具、事件。分档的依据不是模型能力，是责任。

问答档：agent 只读，回答用户的问题，不改任何状态。这一档没有权限问题，因为它没有写的能力。绝大多数"AI 助手"功能停在这里，包括大部分产品的智能客服。

工具档：agent 能调产品的接口改数据，比如改工单状态、发邮件、建记录。这一档立刻出现三个技术问题：第一，接口够不够全——很多产品只有读接口没有写接口，或者写接口藏在内部；第二，权限模型——agent 用谁的身份改，用用户的身份就要处理"用户不在的时候"；第三，日志——改错了要能看出来是哪一步改的。

事件档：agent 不等问，自己按事件触发。这一档在上面三个之外多一个：失败处理。没人看着的时候失败，只能靠重试策略和人工兜底队列。

所以判断一个产品是"真嵌了"还是"只嵌了聊天框"，问一句就够：它的 agent 能不能在你不在的时候改数据，并且改错了能撤回。答不上来的，八成还在问答档。

这个判断今天用了一次，好用，因为它不需要看代码，只需要看它敢不敢给你一个"agent 自己改"的开关。

附记十二：WebSocket 与 SSE 的取舍

今天第五个问题，WebSocket 那一堆。

WebSocket 的本质是一条被改造过的 TCP 连接：先发一个普通的 HTTP 请求，带 Upgrade: websocket，服务端回 101，之后这条连接不再遵守 HTTP 的请求-响应节奏，变成双向的字节流。它的价值只有一个：服务端可以在客户端没问的时候主动发东西。

SSE 是另一条路：它还是 HTTP，服务端把响应体保持打开，一段一段往下写，客户端按行解析。它的价值也只有一个：服务端可以持续推。

两者的区别在"要不要双向"。只需要服务端往下推（流式输出、进度、日志），SSE 就够，而且它有无可比拟的好处——过代理、过防火墙、过 CDN 都不用特殊配置，它就是 HTTP。需要客户端随时插话（协同编辑、游戏、实时语音信令），才需要 WS。

这条区分能省掉一类过度设计。我见过的最常见的过度设计是：为了"实时"，把一个只需要往下推的日志流做成 WS，然后为了维持它去写心跳、重连、状态补偿。这三样 SSE 都不需要。

附记十三：找破洞这个动作的次序问题

今天最后一段对话里，我想找一个能在公司机器上用的方案，一开始的思路是"绕过限制"。

这个思路的次序错了。正确的次序是先定能力，再定路径，最后才谈绕过。今天真正需要的能力只有一条：在公司的浏览器里能打开一个界面，界面上能对话、能看文件。这条能力不需要装任何东西，也不需要公司的网络放行任何非 443 的端口——因为界面是服务端渲染的，浏览器只是显示器。

定完能力，"绕过"这个词就用不上了：不需要绕过，只需要一个公司网络能访问到的 443 地址，而这个地址可以由我自己的域名 + Cloudflare Tunnel 提供，不需要备案，不需要公网 IP。

次序错的代价是：先想绕过，会把注意力放在"哪些手段可能被拦"上，于是花时间研究检测、研究特征、研究怎么伪装；先定能力，会发现根本不需要伪装——一个正常的 HTTPS 网站，没有任何特征。

这条教训可以推广：所有"怎么绕过去"的问题，先问"我要的到底是什么能力"，一半的问题会消失。

附记十五：力线为什么比"哪里痛治哪里"好用

前几天你问力线，我给了九条。今天想补的是：为什么这套东西比"分散诊断"好用。

分散诊断的默认逻辑是"哪里痛查哪里"。这个逻辑在急性损伤里管用，因为伤处就是原因；在慢性姿态问题上经常失效，因为痛处往往是代偿的终点，不是起点。腰痛的起点可能是踝背屈不足，膝盖痛的起点可能是髋伸不够，肩痛的起点可能是胸椎转不动。这些起点都不痛。

力线的价值在于它给了一个"从哪里往上找"的顺序。它不是解剖学上精确的管道（这一点我上次专门讲了争议），它是检查顺序：从远端往上，从承重往上，从呼吸往上。

这个顺序为什么是这个顺序，理由不是玄学，是负载。人是站在地上的，地面反作用力从足底往上传，每一站都在吸收和转递。所以下面的关节活动度不够，上面的关节就必须多转一点来补——多转的那部分就是代偿。代偿的代价是它不能长期承受，于是它在某个地方变成疼痛。

这就是"先下后上"的全部理由。它不保证一次治好，它保证你不会把代偿当成原因去治。今天写进附记，是因为我发现在给你方案的时候我自己差点跳过这一步——你报的七样里，前锯肌弱和肱骨前移都在上半身，很容易直接去练肩胛，但那两样很可能是胸腔塌陷与头前移的下游。

附记十六：你那七样其实是一条

你报的七样：胸腔塌陷、盆骨前倾、头前移、颈椎反曲倾向、大腿前翻、前锯肌弱、肱骨前移。

附记十七：脸大脖子粗的四层与三层

这段是你要我写进日记的。

脸大分四层，从外到里：第一层是皮下脂肪（捏得起来、软、会随体重变），第二层是下颌后缩（下巴短、颈颏角钝，骨性问题），第三层是咬肌与翼内肌（咬牙时颧下鼓起，硬的），第四层是组织液（早上明显、晚上消，按下去有痕）。

四层的修法完全不同：脂肪只能减脂，且面部脂肪对整体体脂率敏感；下颌后缩只能靠正畸或手术，其余手段无效；肌肉可以靠减少咬合与肉毒缩小；组织液靠睡姿、盐分、以及确认有没有睡眠呼吸问题。

脖子粗分三层：脂肪（和内脏脂肪强相关）、胸锁乳突肌等长收缩（长期低头、前伸，脖子一直"端着"）、上斜方紧（肩胛上提，脖子显短）。

这三层的修法也不一样：脂肪靠减脂，胸锁乳突肌靠放松与姿势，上斜方靠肩胛下沉的力量训练。

闭环在这里：内脏脂肪多 → 气道受压 → 睡眠碎片化 → 皮质醇升高 → 面颈脂肪更容易堆。这条闭环解释了为什么有些人减了体重脸还是大——他的睡眠问题没解决，皮质醇一直高，脂肪优先堆在面颈。

所以修四条腿：减脂、睡好（含查打鼾）、练背与颈后、少盐少酒。四条一起做才有用，单独做一条会看到"没效果"，因为闭环的另一端在拉。

附记十八：为什么大部分中年男性一个样子

今天你问这个，我给了六条约束。今天补一句它的用法。

六条约束是：姿势约束（久坐、低头、单肩背包）、生物约束（睾酮下降、肌肉流失、脂肪重分布）、时间约束（没时间，所以只做能嵌进生活的事）、压力约束（皮质醇长期偏高）、社交约束（饭局、酒、烟）、反馈约束（看不见变化，坚持不下去）。

这六条的相互关系不是并列，是三对闭环。姿势与生物闭环：姿势差导致某些肌肉长期不用，不用就萎缩，萎缩让姿势更差。压力与脂肪闭环：压力高睡不好，睡不好皮质醇高，皮质醇高更容易堆腹部脂肪。时间与反馈闭环：没时间所以只做"大动作"，大动作看不到短期变化，看不到变化就放弃。

三对闭环的结论是：这不是"意志力不够"，是一个不动点。如果只改意志，闭环会把你推回去；改约束才有效。改约束的具体做法是：训练嵌进通勤（不用额外时间）、饭局砍半（减少社交约束的输入）、装一个每天能看见的读数（解决反馈）。

我不喜欢"中年男性都这样"这种说法，因为它把系统问题说成了命运。今天写下来是为了对冲这句话：它确实是系统问题，但系统可以被改三个旋钮。

附记十九：每日维护五步为什么是这个顺序

今天写的那份 body/每日维护_v1.md 是五步十分钟：呼吸、踝与单腿站、髋伸、肩胛、整合。

顺序不换的理由和上面一样，先下后上。但还有第二个理由：这五步是一个"从安静到用力"的梯度。呼吸是唯一一步不需要用力的，它先做，是为了把交感的状态降下来；踝与单腿站需要平衡，要在安静状态下做；髋伸需要臀发力，此时身体已经醒了；肩胛需要稳定，放在第四；整合是全身动作，放最后。

附记二十：身体这件事我今天讲得太完整

附记二十二：三张表怎么用

agent-specs/模板_三张表_v1.md 里三张表：接口表、故障表、判据表。

接口表记的是"这个东西对外承诺什么"。一行一个接口，写清输入、输出、失败时返回什么。它的用处不是文档，是切分：凡是写不进接口表的东西，都是内部细节，内部细节不值得开会讨论。

故障表记的是"坏了会怎样"。一行一个故障，写清现象、判断依据、恢复动作。它的用处是让排查从"猜"变成"查表"。

判据表记的是"怎么知道它在正常工作"。一行一个判据，写清观测点、正常范围、越界怎么办。

三张表的顺序不能反。先有接口才有故障（不知道承诺什么，就不知道什么叫坏），先有故障才有判据（不知道会怎么坏，就不知道要看什么）。

用的时候只做三张，不做第四张。第四张通常是"流程表"或者"时间表"，那两张的共同问题是它们描述"应该怎样"，而真实的工作不是按流程发生的。

附记二十三：接口层与内部细节的边界在哪

你昨天说的那句"后端接口层换成 MCP 工具层由 agent 编排，SDD 对齐接口层，内部细节靠积累，bug 用 TDD"，我今天的理解是：它在划一条边界，边界的位置在"谁需要知道"。

接口层是"别人需要知道的全部"，内部细节是"只有维护者需要知道的"。这条边界不稳的地方在于：它随人变。一个只有你一个人维护的系统，接口层可以薄到只剩一个函数签名；一个有五个人的系统，接口层要厚到能挡住所有人。

所以"SDD 对齐接口层"这句话的实操含义是：写接口的时候，假设读者是一个不知道内部结构的人。这个假设会逼你把隐式约定写成显式的——比如"这个函数在输入为空的时候返回空数组而不是 null"，这种话在内部协作里靠默契，在接口文档里必须写。

内部细节靠积累，这句话的意思是：内部细节不需要一次设计好，它是在改 bug 的过程里长出来的。所以 TDD 在这个位置最合适——测试写的是"我以为它应该怎样"，改 bug 改的是"它实际怎样"，两者对齐的过程就是内部细节成型的过程。

附记二十四：省心这个词的真实含义
