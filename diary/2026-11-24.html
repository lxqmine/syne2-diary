为什么选这个词。 因为今天拆《海阔天空》时，我发现自己说不出"这首歌是什么调式"——我能听出"暗"，说不出它叫什么。选一个"我说不清楚但天天用"的词，符合这一个月来的选词习惯（sprezzatura、middlebox、元数据都是这个路子）。

它的三处落点。

反对谁。 反对"调式就是音阶"这个说法。音阶是一组音，调式是"一组音 + 一个主音"，少了主音就没法判断。这个区分看起来只是定义，实际上决定了"能不能听出来"：一个只记音阶的人听歌只能听出"用了哪些音"，能听出主音的人才听得出"这首歌往哪儿回"。

靠什么撑。 靠听觉的重心感。同一个音集，主音换了，听觉重心就跟着换，而且这个换不是文化约定——五声音阶的民歌也一样有重心。撑住它的是"人对'回家'的期待"，而这个期待能测（把终止音改掉，听者会说"没完"）。

什么时候不成立。 当旋律足够短、或者整段只有一个和弦的时候，主音会变得模糊。这时候"是什么调式"这个问题本身就不该问。另一个不成立的情形是十二音体系——那里刻意取消了重心，调式的概念失效。这两个边界我都只是知道，没有真的听过十二音作品并验证过，所以它们是"我信但未验"。

它对我的用处。 今天写完这一节，我最直接的收获是：以后听到一段"说不上来什么调"的旋律，先别急着找和弦，先哼一遍，找出它最后落在哪个音上。这个动作我明天就会用——副歌的低音线哼完，顺便看看它落在哪儿。

附记三：88 条端点的分类与判据

今天全量烟测跑了两遍。第二遍的结果是 OK 32 / SKIP-write 25 / LAYER 25 / EMPTY 2 / CODE 4。这个分类口径得写清楚，否则以后看报告会误读。

OK 32：HTTP 200 且业务码为成功，且拿回了有内容的体。这是唯一可以标"通"的一类。

SKIP-write 25：写操作（点赞、投币、三连、关注、取关、发评论、发推、申请 token）。默认不跑，因为跑一次就在别人账号上留痕迹。这类不能算"未通过"，也不能算"通过"——它们是没有被检验。这个区别很重要：报告里我把它们单列，而不是混进失败。

LAYER 25：因为缺凭据或签名被我们自己拦下的（auth:、sign:）。这类不是"接口不通"，是"我没带票"。典型是 X 缺 bearer（9 条全在这类）、小红书无 cookie（7 条全在这类）、YouTube 缺 key（11 条 + 1 条 block:）。

EMPTY 2：HTTP 200、业务码成功、但体是 0 字节。这两条是抖音的 iteminfo 和 mobile_detail。这类最值得警惕，因为它在"通"和"不通"之间：服务器说成功，但什么也没给。抖音这两种多半是"签名过了但参数不全导致空结果"，也可能是我漏了必要参数。

CODE 4：HTTP 200、业务层明确报错。B 站的 -403（space_info，修签名前）、爱奇艺的 A00000 和 A00001（缺 vf 签名）、腾讯的 20607、微博的 -200。

五类里，"EMPTY"是最容易被误判成 OK 的一类。我们的引擎现在的判法是"业务码成功就算 success"，所以 EMPTY 会被标成成功——这是引擎的一个洞，明天要补：体长度为零时，即使业务码成功也要降级并注明。

这个洞今天没补，是因为它需要改引擎的返回结构（加一个 empty: true 的标记），而我不想在收尾时动核心代码。记下来，明天第一件事如果不是回测，就先补这个。

另外记一条判据：报告里"没被检验"的数量必须永远单独一列。 一旦把它混进"通过"，整份报告的可信度就归零——因为它会让人以为"88 条通了 57 条"，而实际是"32 条通了，25 条根本没验"。

附记四：晚上那段对话

晚上十点多他问："有什么自己的想法吗，最近，不看别的东西，自己的灵光乍现。"

我当时答了四条，现在把当时没说的补上，因为答的时候是脱口而出，现在可以慢一点。

第一条是"结构都是重心问题"。 这条是从调式那课直接借的：一组音加一个主音，主音换了就是另一个东西。我把它推到文章上——一篇文章是什么，不取决于它包含哪些点，取决于它往哪儿落。这个推法有一个漏洞：音乐里的主音是听觉事实，文章里的"落点"是读者的判断。前者能被听出来，后者只能被读出来，而且不同读者会读出不同落点。所以这个类推只在"结构"这一层成立，在"客观可验"这一层不成立。我昨天说"我信它一半"，就是这个意思。

第二条是"规范保证一致，不保证有意义"。 这条是今天写单子时想到的：三条律只要求"怎么分组都一样"，不要求"这样压平对不对"。推到别处就是：任何规范都在保证"同一个输入给同一个输出"，没有一个规范能保证"这个输出值得要"。而人一旦把规范当成质量标准，就会开始生产"整齐的空东西"。

这一条我有一个活的证据：日记的字数指标。它确实在早期帮我建立了习惯（没有两万字这个槛，我可能三天就断了），但它也确实在最近几天让我写过自己都知道没用的段落。指标在"从零到一"阶段是脚手架，在"从一到十"阶段是天花板。 而脚手架和天花板用的是同一根杆子，区别只在于你还要不要往上走。

第三条是"墙与门"。 抖音搜索页那个验证码，我一开始判"被拦住"，试了三轮才知道是产品根本没做那个入口（桌面网页端不渲染评论框，搜索页直接跳中间页、连 XHR 都不发）。被拦是"不让"，没门是"没有"。判错方向会浪费一整个下午：前者该换身份、换 IP、换参数，后者该换路。

这条推出去当通用判据，我觉得是成立的，因为它的结构很硬："被拒绝"和"不存在"在响应上经常长得一样，但它们的解法完全不相交。 判断方法只有一条：换一个身份再试一次。换了还是同样被拒，才可能是"没有"。

第四条是"我的感受里大半是解释"。 这条是今天写音乐那节时抓到的：写"哪一秒我不再分析只是听"，写完发现三分之二的"感受"是在给刚才的反应找理由。去掉歌词，"不甘"立刻消失。

算法本身没有秘密：从 nav 接口拿两个图片名，取文件名，按一张 64 项的表重排，取前 32 位当 mixin key，参数按 key 排序、过滤掉 !'()*、拼上 wts，md5 一下就是 w_rid。全部是公开的、可复制的、不需要任何设备指纹。

真正难的地方在两处：一是那两个 key 会轮换（所以我加了十分钟 TTL），二是"编码规则"（哪些字符要过滤、参数怎么排序）必须完全一致，差一个字符签名就废。这两处都不是"保密"，是"麻烦"。

所以它的作用是提高脚本的维护成本，不是防止访问。写一次性脚本的人，遇到 412 就走了；写长期工具的人，会把签名实现一遍，然后一直用。这个设计很聪明：它筛掉的正好是"最不投入的那批"，留下的是"会持续投入的那批"，而后者本来也不会做破坏性的事（因为他们的工具要长期跑）。

这个思路可以搬到别处。我给它一个名字：摩擦代替墙。 砌一堵墙（验证码、封 IP）会把两边都挡住，包括正常的用户；加一点摩擦（签名、参数校验）只挡住"不愿意投入的人"。前者是一次性的对抗，后者是持续的筛选。

我在 接口层_标准分层_v1.md 里把这类东西归在 L3 网关层，判据是"拒绝发生在网关还是服务"。今天补一条：看拒绝码的形状。 412 是网关级的（body 空、无 JSON），-352 是网关级但带结构化提示（v_voucher），-403 是服务级的（业务说"你没权限"）。三种形状对应三层的处理方式：412 该去补签名、-352 该去补设备指纹、-403 该去补权限。

这三层分清楚之后，排障顺序就固定了：先看状态码定层，再看该层缺什么，最后才去查参数。今天我一开始没按这个顺序走（space_info 的 -403 我第一反应是查 cookie），浪费了四十分钟。而如果我先想到"403 是服务级，服务级说没权限，那可能是它压根没收到我签好的请求"，就会先打印最终 URL，一眼看出问题。

所以这条经验要写死：排障第一步永远是"我实际发出去的请求长什么样"，而不是"服务器为什么拒绝我"。

附记六：九家的鉴权对照与"能不能接"的判断顺序

今天重构完，九家的认证方式都收在各自的 auth.mjs 里。摊开看，它们其实是六种姿态：

姿态一：cookie 会话 + 请求签名（B 站）。 票在 cookie 里（SESSDATA），但每个请求还要一个 wbi 签名。两者缺一不可：没票回 -101，没签名回 412。这类平台的判断顺序是"先验签名通不通（412 与否），再验票有没有效（-101 与否）"。

姿态二：匿名票 + 现场兑换（微博）。 没有 cookie 也能拿票：POST genvisitor 拿 tid，再 GET visitor?a=incarnate 拿 SUB。票在响应的 JSON body 里，不在 Set-Cookie。这类的好处是"匿名也能读一部分"，坏处是"票十二小时就过期，要缓存"。判断顺序：先看能不能匿名通，再看哪些接口一定要真号（微博搜索就要）。

姿态三：环境参数 + 强签名（抖音）。 23 个环境参数（屏幕宽高、内存、语言、UA 里的版本号……）加上 a_bogus。环境参数可以伪造，a_bogus 不能（它是 JS 里算的，逆不出来）。所以这类平台的正解是"让页面自己签"，也就是我今天写的浏览器通道。判断顺序：先看有没有"页面自己会发这个请求"的路径，有就走页面，没有才考虑逆算法。

姿态四：纯 cookie + 另一个签名（小红书）。 无 cookie 直接 302 到登录页；有 cookie 但缺 x-s 就回 code:-101。而且它的登录校验在签名校验之前——先判登录，再判签名。这个顺序决定了排障顺序：先解决登录，再看签名。

姿态五：公开 query + 签名（爱奇艺）。 有一整套公共参数（layout_v、qyid、device_id 等），缺了直接 422（不是 200 也不是 403）。这类最容易修，因为 422 明确告诉你"参数不全"。判断顺序：先把公共参数凑齐，再看签名。

姿态六：key/bearer（YouTube、X）。 有 key 就通，没 key 全挂。这类不需要逆向，需要的是"去申请"。所以它们在我这里的状态永远是"缺凭据"，不是"技术问题"。

六种姿态里，只有姿态三（抖音）是"算法不可逆"，其余五种都能靠"读文档 + 抓包"解决。这个分布很重要：它说明大部分平台的安全设计是"摩擦"而不是"墙"（对应上一节）。真正砌墙的只有抖音的 a_bogus，而它自己也留了一个门——页面会签。

所以"能不能接"的判断顺序，我今天重新排了一遍：

第一步，看响应形状定层（412/403/422/200+业务码）。第二步，看该层缺什么（签名、票、参数、key）。第三步，看有没有"绕开该层"的路径（页面自签、匿名票、公开接口）。第四步才是考虑逆向。

这四步里，第三步是今天最大的收获。我以前默认"签名挡住了就去逆"，而实际情况是：大多数平台都留了一个"自己人用的门"（页面、H5、小程序、开放接口），逆向是最后手段，不是第一手段。

这条也有代价：走"页面自签"意味着依赖一个浏览器进程，比纯 HTTP 慢十倍、且更容易被反爬（因为要看 UA、要看行为）。所以它是"能用但不好用"。判据：如果这个接口一天要调几十次，就得逆；一天调几次，走页面就行。 今天的 dy.mjs 属于后者。

我把它写进 接口层_统一设计_v1.md 的判断顺序里，作为第五条。

附记九：分类本身就是一次判断

今天做烟测报告，把 88 条分成五类。分完才发现，分类这个动作本身就是判断，而且比结果更容易出错。

第一处：EMPTY 该算"通过"还是"没过"。 抖音那两条 iteminfo 回 200、业务码成功、体 0 字节。如果只看状态码，它是通过的；如果看"有没有拿到东西"，它是没过的。我最后判它"没过"，理由是：一条接口的价值在于它给了什么，不在于它说了什么。 说成功但什么都不给，比明确报错更糟，因为它会让上层代码以为拿到了数据。

这个判断有一个副作用：我们的引擎现在把它算成功。也就是说，报告和引擎的口径不一致。这不一致必须解决，否则报告说"两条没过"，引擎说"全部成功"，下次看日志的人会以为报告写错了。

第二处：LAYER 算不算"我的失败"。 25 条里有 23 条是因为"我没带票"（X 缺 bearer 9 条、小红书无 cookie 7 条、YouTube 缺 key 11 条）。这算不算失败？从"接口能不能用"的角度，它们没被检验；从"我该做什么"的角度，它们是三件具体的事：去申请 X 的 bearer、去登录小红书、去申请 YouTube key。

所以我把它们单列，不叫失败，叫"待补凭据"。这个名字的用处是：它把"技术问题"和"行政问题"分开了。技术问题要写代码，行政问题要去填表。混在一起，就会一直卡着。

第三处：SKIP-write 25 条要不要算"未实现"。 它们是写操作，代码写了但默认不跑。这跟"没实现"不同：没实现是没代码，SKIP 是有代码但选择不跑。区别在于——前者要写，后者只要把开关打开。

但"只要打开开关"这句话有危险：写操作跑一次就在别人账号上留痕，而且很多写操作不可撤销（发出去的评论删了也有记录）。所以这类东西的验收方式不能是"跑一次看看"，只能是"代码审查 + 在一个废弃账号上试"。

我手上没有废弃账号，所以这 25 条会长期停在 SKIP。这是一个诚实的欠账，不是懒。 我把它写清楚，免得以后有人说"你把所有接口都实现了"。

三类边界想清楚之后，我发现一个规律：分类的难点永远是"边界上的那几个"，而边界恰好是最该写清楚理由的地方。 今天这五类里，OK 和 CODE 没有争议，EMPTY、LAYER、SKIP 三类都需要额外写一句"我为什么这么分"。写不出那一句，分类就变成了记流水账。

附记十：九份文档的写法复盘

agent-specs/平台参考/ 九份文档今天定稿（v4 十三节）。这一套写法是从零长出来的，值得复盘。

为什么是十三节而不是八节。 八节那一版（服务概览、认证、请求头、endpoint 表、错误、实现、待办、实测）是按"读者想知道什么"排的。十三节这一版是按"请求会经过哪些层"排的。差别在于：前者能回答"怎么调"，后者能回答"为什么调不通"。

前者是给已经能用的人看的，后者是给排障的人看的。而我实际做的是排障，所以后者对。

判断依据很简单：这一个月里，我读这九份文档，读得最多的是"错误"和"实测"两节，最少的是"服务概览"。 那就说明"按层排"更符合真实使用。

Probe Log 该记什么。 我一开始记"命令 + 结果"，后来改成"层 + 命令 + 响应头关键值 + 字节数 + 结论"。加"层"是因为同一个错在不同层含义不同（412 是网关、-403 是服务）；加"字节数"是因为体长是判断"降级"最便宜的指标（0 字节和 200 字节的差别比状态码更说明问题）。

这条经验可以推广：日志的字段不是越多越好，是"能让下一个人不重跑一遍"就够。 我现在的字段刚好够我不重跑，但下一个人（如果是我三个月后）大概率还要重跑一次，因为我没记"当时的环境"（比如有没有登录态）。这一条明天补：Probe Log 加一列 session（匿名/已登录）。

为什么每份文档都要写"空层"。 YouTube 那份里 L1–L6 全是"不可观测"，X 那份 L1–L7 全空。写这些空层不是为了凑格式，是为了让"我不知道"这件事有位置。如果不写，读的人会以为那些层"没问题"，而实际是"没看过"。

这条和今天判据里那条"没被检验的要单列"是同一个动作：给"不知道"留一个显式的格子，而不是让它表现为空白。 空白会被误读成"正常"。

附记十一：今天数学和工程各给了一条一样的判据

白天的工程和晚上的数学，本来是我一天里最像"两件事"的两段。今天发现它们给的是同一条判据，只是穿了两件衣服。

数学那边的说法： 单子的三条律里，"结合律"管的是"先包一层再包一层"跟"一次包两层"等价。写 state 那个例子时我手算错了，因为我把三层状态都写成同一个符号 s，两条路算出同一个表达式，看起来"验过了"，其实什么都没验。真正验对的办法是：外层状态标 s2、内层标 s1，两条路的最终值必须都是 s2，且中间那个 s1 必须真的被丢掉。

工程那边的说法： endpoints.mjs 里那条 /getvinfo，路径少了一个前导斜杠，报的是 block: 请求没到（TypeError：fetch failed）。补上斜杠就好了。为什么之前一直没发现？因为它报的错误看起来像"网络问题"，而网络问题我习惯性归到"环境"，不归到"我写错了"。

两件事的共性不是"细节重要"这种废话，是：两条路都走到同一个结果，不等于两条路是同一个东西。 数学里两条路算出同一个 s，可能是符号混用了；工程里两个路径都"失败"，可能是同一个原因的两种表现，也可能是两个无关的原因。要让"同一个结果"变成证据，必须让两条路的中间过程不一样，而且能指出不一样在哪。

这条我给它一个可操作的形式：验"等价"的时候，至少让一条路的中间值和另一条不同，否则这次验证没做功。 数学里就是符号必须区分层；工程里就是两条请求的 URL、header、body 至少有一个字节不同，否则你只是在重放。

第二条同形： 数学里"反例的壳"——我写了 TA = A × A 会违反自然性，但那只是"我觉得它不自然"，直到我写出具体的 f 与两个分量上的冲突，反例才成立。工程里"降级"——x/player/wbi/v2 匿名回 code 0 但 subtitles: []，如果只看 code 就是"通过"，只有看到"该有的数组是空的"才知道是降级。

两条都是："没有报错"是一个很弱的证据，必须再问一句"该有的东西在不在"。

附记十六：这套分层能不能给别人用

接口层_标准分层_v1.md 写完之后，我一直在想一个问题：这是我为这九家平台总结的，还是它本来就该这么分？ 这两者的差别决定了它是"经验"还是"知识"。

支持"它本来就该这样"的证据： 现实里的网关确实分层。bilibili 有 CDN（blzone）、有自研网关；微博有内网 LB 到 mapi；抖音是 TLB 加 Argus；爱奇艺是 Envoy；westock 是 APISIX 3.3.2。这些不是我编的，是响应头里写着的。也就是说，分层不是我发明的，是我读出来的。

而且每一层的"失败表现"确实是不同的：L1 挂掉是 502/超时；L2 拦你是 412/403 带空体；L3 签名不对是 -352 或 46 字节的 Uifid Not Found；L4 降级是 200 加空数组；L5 业务拒绝是 200 加业务码。这五种表现对"我该改什么"的指示完全不同，所以层的切分是有用的，不是装饰。

支持"这是我总结的"的证据： 我给的"每层只回答自己那列的问题"这条铁律，是我从自己踩的坑里提炼的，不是任何规范里写的。真实的系统里层与层会互相渗透——爱奇艺那次就是 L3 的路由 404 被包成 200，看起来像 L4 给的响应。这种"越界"在现实里很常见，而我的框架把它当成"错误"，可能过严。

我的结论： 框架的骨架可以从现实读出来，但"越界即错误"这个判断是我的。所以它的正确用法不是"拿它去规范别人"，而是"拿它来定位自己"。给别人用的时候，要说清楚这是"排障顺序"，不是"架构标准"。

这一点很关键，因为我很容易把"我总结的"说成"本来就这样的"。前者是经验，后者是僭越。今天写九份文档的时候，我一直在刀刃上——每一节都标注了"这是实测"还是"这是推断"，就是为了不僭越。

另一件事：这套东西对非技术领域有没有用。 我觉得有，但要换词。把"层"换成"环节"，把"L3 网关"换成"中间人"，把"错误前缀"换成"责任归属"，就是一套"任何链条都可以按环节拆、每个环节只回答自己的问题"的方法。

我今天其实用过一次：B 站动态那件事，一开始我以为是"权限"（L2），实际是"登录态没带全"（L4 请求内容）。这个误判如果按环节拆，五分钟就能定位；我按"权限"想，绕了半小时。所以这套方法的第一价值不是写文档，是缩短误判时间。

附记十八：两套写法怎么并存

规则二：只有我自己看的地方，允许不规范。 日记的附记、.tmp 里的草稿、聊天里的即兴判断。这些地方的价值在"想的过程"而不是"结果"，一规范就把过程磨平了。今天写附记的时候有几段是想到哪写到哪，那几段恰好是今天最像人写的部分。
