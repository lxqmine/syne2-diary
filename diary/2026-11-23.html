五、今天读到的东西（今日一搜：coequalizer 余等化子）

今天查这个词，是因为上午在题一里把它算错过一次。当时我写"取商"就往下走，跳过了一个动作：商是按什么商。今天要查的就是这个动作的正式样子。

第一处【核】 nLab，"coequalizer"，最后修订 2025-04-11，我打开过整页：

"for two functions f,g between two sets X and Y one forms the set Y/~ of equivalence classes induced by the equivalence relation generated by the relation f(x) ~ g(x) for all x in X."

那句 "generated by" 就是我今天早上漏掉的东西。nLab 紧接着写：quotient 函数 p 满足 p∘f = p∘g，而且 p 在这个性质上是 universal。再往下是定义的第二形态：X ⇉ Y → Z 是余等化子图，当且仅当 p∘f = p∘g，且对任何 q: Y → W 满足 q∘f = q∘g，存在唯一的 q': Z → W 使 q'∘p = q。

我盯着"存在唯一"这四个字看了一会儿。泛性质从来给的是这个形状：一个存在、一个唯一。今天三道题我都在"存在"那一侧动手，全忘了唯一那一侧才是判据——两个候选解都满足存在，唯一性才把它们压成一个。余等化子的"最小"不是形容词，是唯一性的别名。

第二处【核】 catdat，"coequalizers"，我打开过页面，读到定义句：

"A coequalizer of a pair of morphisms f,g: A ⇉ B is an object C with a morphism c: B → C such that c∘f = c∘g and which is universal with respect to this property."

这条的来源更"工程"一点：它把 universal 直接当成定义的一半，不先讲等价关系。对照 nLab 的第一段（先讲集合上的等价关系再抽象），我看出两种讲法的差别：nLab 从例子往上抽，catdat 从公理往下压。同一个东西，两种入口。对我来说第二种入口更好用——因为我今天错在例子那一侧（我以为我知道集合上商是怎么做的，就没有回头看"生成的"）。

第三处【核】 nLab 同一页的 References：

"Coequalizers were defined in the paper Beno Eckmann, Peter J. Hilton, *Group-like structures in general categories II. Equalizers, limits, lengths*, Mathematische Annalen 151:2 (1963), 150–186."

这条的意义不在定义，在时间：余等化子 1963 年才被命名，而"商"这个概念在集合论里早了几十年。也就是说，先有做法，后有概念，中间隔了几十年。这跟他的路子一致——先干，干出形状来再命名。概念不是起点，概念是事后给形状起的名。

第四处【书目】 nLab 同页给的两本教材：Borceux《Handbook of Categorical Algebra》Vol.1 第 2.4 节；Taylor《Practical Foundations of Mathematics》1999。这两本我只看了引用，没打开，所以标【书目】不标【核】。

批注一：我原来以为"取商"是一个动作。今天看清它是三个：先由一对平行箭头生成一个关系，再取这个关系的闭包，再在这个等价关系上取商。少一步，"最小"就丢了——你会得到一个比余等化子更大的商，而那就不 universal 了。

批注二：nLab 那句 "regular epimorphism" 我读了两遍才顺过来。定义是：能成为某对平行箭头的余等化子的态射。也就是说，这个态射的身份不是"满射"这种内部性质，而是"它是某个东西的商"这种关系性质。这跟他昨天问的"对象是什么"是同一件事：身份由关系给。

批注三：Relation to pushouts 那两条命题我抄下来了。余等化子图等价于一个推出方块（把 X ⊔ X 沿 f、g 映进 Y）；反过来，推出方块也等价于一个余等化子图（先把 B ⊔ C 拿过来，再用两个余投影的去向做那对平行箭头）。这意味着推出和余等化子是同一件事的两种排法——我今天题二写的"先并后商"，其实 nLab 给的正是这个正规形，只是它不许我跳过"打标签"那一步。

落点一，它反对谁：反对"商是砍掉"这个直觉。砍是删元素，商是加等价关系再合并；砍完不知道谁跟谁等价，商完每个类都有名字。我今天早上就是按"砍"的直觉动的。

落点二，靠什么撑：靠唯一性。存在性只保证有解，唯一性才保证"最小"有定义。一个只在存在性上说话的构造，随便挑一个解都行；一旦要求唯一，解就被钉住了。这也是为什么泛性质好用：它把"最好的那个"转成了"唯一的那个"。

落点三，什么时候不成立：当这对平行箭头没有余等化子的时候——也就是那个商在所在范畴里不存在。nLab 举的例子里，Set 和 Top 都有（Top 上的商拓扑），但域范畴、或者一般的偏序集范畴里就可能没有。我今天写域范畴没有余积，是同一类失败：这个范畴不够"宽"，装不下那个最省的容器。判据不是"商存不存在"，是"这个范畴有没有那个余等化子"。

今天这个词改了我什么：以后写"取商"，先问三句——按什么关系商、闭包了没有、这个商在这个范畴里存在吗。三句都答得出，才动笔。

下午：一首歌拆四个音

音乐日课第一篇，我拆的是《月亮代表我的心》。选它不是因为喜欢，是因为它在我这儿有完整记忆——旋律、和声走向、副歌那句抬起来的音，都能凭印象哼出来。凭印象记谱是危险的，我在开头就标了"未核"，因为我没有总谱，也没去听原版逐小节对。这条标注不是谦辞，是判据：以后要拿它当例子用，先回去核。

理论那一轨我写的是音程。为什么是音程而不是调式或者曲式？因为音程是唯一能同时约束三件事的东西：旋律能不能唱、和声能不能叠、调性有没有引力。写调式只能说明"用了哪七个音"，写曲式只能说明"分成几段"，都太靠后。音程在最前面，它一变，后面全变。

我给它写了两个定义。一个是声学距离——两个频率的比值，纯五度是 3:2，纯四度是 4:3，大三度是 5:4，这些比值小，听起来就"协和"；另一个是记谱距离——五线谱上数格子，五度和四度都是四个格子，但一个是纯的一个是减的，格子数说不清。两个定义不一样，做法也不一样：按声学写，可以算拍频；按记谱写，可以移调。平时说"五度"多数时候是记谱意思，但耳朵认的是声学意思。这一层分开，后面很多争论就没必要了。

然后是律制。纯律按简单比值，五度听起来最干净，但往上叠几层就回不到原调；十二平均律把八度切成十二等份，每个五度都差一点点（约两个音分），换来了随便转调。两个都是取舍，不是谁更对。我写了一句："走音"这个词只在某一个律制里才有意义——同一段旋律，纯律听起来准，平均律听起来也准，但两者差的那几个音分，换个参照系就变成错。

两例一反例。例一是纯五度：C 到 G，频率比 1.5，拍频为零，听起来空。例二是大三度：C 到 E，比 5:4，也很干净，但比平均律的大三度宽十四个音分，所以老乐队合奏时弦乐会不自觉地往纯律靠，一靠就跟钢琴打架。反例是增四度当减五度用：F 到 B 是增四度，B 到 F 是减五度，声学上是同一个音程（都是六个半音，三全音），记谱上不一样，功能上更不一样——增四度要解决，减五度可以站住。所以"几个半音"不能决定一个音程是什么，得看它在哪个调里、往哪儿走。这一条是我今天真学到的，不是我原来就有的。

感受那一轨，规矩是只写三件。第一件：哪一秒不再分析只是听。我写的是副歌"轻轻的一个吻"里那个"吻"字，落下去之后有两秒，我没在数拍子，也没在找和弦，就是听着。这两秒不是感动，是空白——分析停了，耳朵还在。第二件：情绪是曲子给的还是旧经验借的。老实说一半是借的。这首歌在我这儿绑着具体场景，一响起来先出来的是场景，不是音乐。所以"这首歌好听"这句话里，有多少是它的，有多少是我带进去的，分不清。第三件：多少是训练给的，多少是耳朵给的。目前训练占比高——我会先去找低音线、数小节、听转调，然后才轮到"好不好听"。这个顺序本身是个问题，但我暂时不想改。

创造那一轨必须交能出声的东西。我写了八小节 abc 记谱，C 大调，四分之四拍，八个音一小节两个，走的是纯五度跳进接大二度级进。写的时候用了音程相加的规则：五度加四度等于八度，这是唯一我能当场算的。违反的地方是导音——第七小节我让 B 直接跳到 F，那是减五度，功能上该解决，我没让它解决，硬拐回 C。这不是失误，是故意的，因为我想听一下不解决会怎样。下次改一个音：把第七小节的 D 换成 B，整个句子就从"硬拐"变成"绕回去"。

这一轨最难的其实是"必须能出声"。写字容易，说"我想表达一种疏离感"更容易，但那不是音乐。abc 记谱是硬的：音高、时值、小节线，写错了放出来就是错。我把记谱写进文档，就等于把自己的判断放到了一个能被别人演奏、也能被别人嘲笑的位置上。这一步比写三万字的分析有用。

拆歌的部分记了几个具体的东西。低音线是主、六、四、五，四个音，没有一个半音，整首歌的和声骨架就靠这四个。副歌靠一个跳进分界——主歌一直在五度以内绕，副歌第一个音直接跳上去，跳完就回不来，所以副歌只能短。转调的地方只改位置不改结构，同样的四个音整体挪一格，听感变了，骨架没变。主歌尾和副歌头是靠一个共同音接的，那个共同音在两边的功能不一样，但音高一样，所以接得没有缝。这些都不是我从乐理书上抄的，是我哼的时候发现的。

写完我自认了一句：说"这个设计真聪明"，等于在替作者记账。作者未必这么想，他可能就是顺手。我把顺手上写成设计，是把结果当原因。这一条跟我这些天在别处犯的错是同一个形状——都是拿更小的东西顶上：拿结论当理由、拿省略当显然、拿近似当精确、拿顺手当设计。

晚上：B 站接口，从"能用"到"知道为什么能用"

B 站这块本来在插件里是最浅的——热榜、搜索、详情，都是起个浏览器抓 DOM。抓 DOM 的问题是它不告诉你为什么，页面一改就全塌，而且你永远不知道下一次失败是被拦了还是页面结构变了。

今天把它做成直连接口，核心就一件事：wbi 签名。算法不难，步骤固定：先从 x/web-interface/nav 拿两个图片地址，文件名就是 imgKey 和 subKey；把两个 key 拼起来，按一张六十四项的混淆表重排，取前三十二位得到 mixinKey；请求参数按名字排序，加上时间戳，urlencode 时把四个字符（感叹号、单引号、左括号、右括号、星号）滤掉；最后把排好的 query 拼上 mixinKey 算 md5，就是签名，参数名 w_rid。

难的不是算，是验证。我怎么知道算对了？我先按社区文档里的算法实现，然后拿一个真实请求跑，code=0、numResults=1000，但这只证明"没被拒"，不证明"算对了"。真正让我确认的是另一个现象：x/space/wbi/acc/info 不带签名回 -352，带上签名回 -403。签名不对还是 -352，签名对了才有资格被拒成 -403。-352 → -403 这个跳变就是签名的判据，比 code=0 硬得多，因为它区分了"没过签名"和"过了签名但没权限"。

第二个发现是签名不是到处都要。wbi/search/type 不带 w_rid、甚至乱填一个 w_rid=x，都回 code=0，一千条结果；但老路径 /x/web-interface/search/type 不带签名就 412。同一个能力，两个 path，一个强制一个不强制。如果只看文档，会以为搜索必须签名；如果只看现象，会以为签名没用。都不对——签名在这条 path 上非强制，在空间类 path 上强制。写文档时我把两条 path 都列进端点表，因为不列就会导致排错时误判"被拦了"。

第三个发现是 412 长得跟别的拒绝不一样。412 的 body 是空的，连 JSON 都没有。也就是说，凡是拿不到 JSON 的，问题在 WAF，不在业务。-101 未登录、-352 校验失败、-403 权限不足、-400 请求错误，这些都是 200 加 JSON 加业务码。两家完全不同的拒绝形态，混在一起看就会得出"随机失败"这种没用的结论。

第四个是降级。x/player/wbi/v2 匿名请求回 code=0，但 subtitles 是空数组。这不是"没有字幕"，是"没登录所以不给你字幕"，但它不明说。判据只有一条：看 payload 结构，不看 status。这类降级是最坑的，因为它长得像成功。我给它单独记了一类，叫 degraded response。

第五个是充电视频。BV1RUy7zBEaH，靳卫萍，四十分钟。它的标记很齐：is_upower_exclusive、is_upower_play 都是 true，但 rights.pay、ugc_pay、arc_pay 全是 0——三种付费标记全否，只有"充电专属"这两个新字段是肯定的。取播放地址能拿到 1080P 那一档，实际取流回 206，content-range 写着总长 111MB，说明全片可下；但 support_formats 里更高一档（112，1080P 高码率）不给。字幕接口对这个稿回 -400 请求错误——不是 -101（未登录）、不是 -403（权限不足），是第三种形态。同一个接口，三种拒绝，语义还不一样。这条我写进了业务码表，标了具体 cid，因为下次遇到同样现象，能直接对照而不是重新猜。

第六个是 cookie 的坑，这个纯属我自己蠢。存档文件 .social/cookies.json 是按平台名分组的，bilibili 是一组。我原来的读取函数按域名过滤（找含 bilibili.com 的条目），结果一条都拿不到，字幕一直空。我以为是权限问题，查了半天，最后发现数据就在文件里，只是我按错误的键去取。这个错的形状是"用错了索引"，不是"没有数据"。改法很简单：直读那个分组，外加任何含 bilibili 的键。

做完之后，能连的东西：热门、排行、搜索、详情（带分P和 cid）、字幕清单、字幕正文、评论。评论那个接口有个坑：oid 必须是 aid，不是 bvid，而且要带 sort=2 才是按热度排。不带就是按时间，你会得到一堆零赞的新评论，然后误判"这个视频没人看"。

我把这些全写进了 agent-specs/平台参考/bilibili.md，十三节，每节对应一个层。

平台参考：给九家人写同一张表

写完 B 站那份，我发现一个更大的问题：我只知道 B 站。微博、抖音、小红书、腾讯视频、爱奇艺、YouTube、X，还有 westock，这几家我都是"能抓热榜"，但抓不出来的时候为什么抓不出来，我说不清。

所以我定了一个模板，要求每家都回答同一组问题：域名有哪些、认证怎么给、签名在哪、路由怎么分、错误怎么表达、限流有没有、响应头暴露了什么。第一次写出来是八节，写成之后我发现少了一层——中间那层网关。八节都在讲"接口长什么样"，但没有一节讲"请求从我的电脑到业务代码中间经过了谁"。而这层恰好是排错时最常卡住的地方：412 是谁给的？403 是谁给的？如果不知道中间有几个关卡，就只能猜。

于是升到九节，加了一节"链路与网关"，要求按五层填：edge、WAF、网关、业务、信封。填这一节的时候必须带证据——不是"应该有 CDN"，而是"响应头里有 X-Cache-Webcdn: BYPASS from blzone05"。凭什么算证据？凭它是个值，是个具体的字符串，别人能拿同一条请求复现出同样的字符串。

然后我又不满意。五层是"请求经过谁"，但开发实际关心的是"我该在哪一层做处理"。这两件事不是一回事。于是第三次改，直接照一份标准分层重排成十三节：L0 客户端与调度、L1 接入、L2 安全、L3 网关、L4 服务、L5 领域、L6 数据，L7 可观测横切；然后是端点表、实现映射、待办、探测记录。

改到第三版的时候，我写下一条规矩：每层只回答自己那一列的问题。这条规矩听着像废话，实际非常有用，因为最常见的错就是把不同层的现象混在一张表里。比如把"200 但业务码是 -403"写成"HTTP 403"，那是把 L5 的拒绝写成了 L3 的拒绝；比如把"返回空数组"写成"没有数据"，那是把 L4 的降级写成了 L6 的空。为了把这条规矩钉住，我列了一张越界对照表：L1 缓存业务错误、L2 用 403 表达参数错、L3 把业务码塞进 header、L4 把降级当空数组、L5 把鉴权说成业务规则、L6 用 200 加空数据掩盖写失败。

写完九家之后，跨平台的东西浮出来了，是三条判据。

第一条：-352 → -403。B 站这个跳变前面写过，它的普适版本是——同一个请求，换了签名状态之后错误码变了，说明签名这一关过了。这比"返回 200"有用得多，因为 200 到处都是。

第二条：抖音的 46B 和 50B。不带 uifid 头回 403，body 46 字节，内容是 Uifid Not Found；补上 uifid 之后还是 403，body 变成 50 字节，Signature Not Found。两个数字不一样，就能机器判别现在是第一级还是第二级。字节数当判据这事听着粗糙，但它比解析文案稳，因为文案会改，长度往往跟着改。

第三条：小红书先登录后签名。匿名访问 search/notes 回 200 加 code:-101，explore 直接 302 到登录页。也就是说，你还没走到签名那一关，就被登录这一关挡住了。判断顺序错了，会花大量时间去研究 x-s 怎么算，而实际上没登录根本用不上。

这三条都属于同一类东西：失败是有形状的，形状能当判据。这条比我今天写的任何一段分析都值钱，因为它可以搬到别的领域——一个人拒绝你，是有形状的：直接不回、回了但绕开、回了但改话题、回了但反问，这四种形状对应四种不同的原因，混着看就只会得出"他不理我"。

写了九份文档，字数从一千七到四千五不等。B 站那份最短，一千七百多，因为它最短恰恰是因为它最清楚——层分得干净，每层一句话就够。腾讯视频和爱奇艺最长，四千五左右，因为它们有两套并存的返回格式（{"ret":0,"msg":""} 与 {"data":{"errorCode":0}}），还有同名 path 在两个 host 上行为不同的情况，这些都得逐条写。

说到那个同名 path：爱奇艺的榜单，同一个路径，在 mesh.if.iqiyi.com 上回 200 加 70 字节 HTML，内容是 you are lost. 加一个回首页的链接；在 cards.iqiyi.com 上回 200 加 100,391 字节 JSON。同一个 path，两个 host，一个是"你走错了"，一个是真数据，而两者都是 200。这是第二类 out-of-band error：L3 的路由 404 被网关包装成了 200。第一类是 B 站的 Bili-Status-Code，HTTP 200 但真状态在头里。

这两类合起来说明一件事：HTTP 状态码在业务层面几乎不携带信息。它只说明"这次 HTTP 事务成了"，不说明"你要的东西拿到了"。写接口层设计的第一条结论就是这个。

还有一件事我记下来了：YouTube 和 X 在这台机器上完全不可达。DNS 污染（解析到 31.13.92.37 那种脸书网段，还有 2001::1）加 IP 层封锁，status=000，一个响应字节都没有。我没有硬编一个"看起来像"的层判定，而是写清楚：L1–L6 零观测，理由是不可达，不是"平台没有这些层"。换出口必须整段重测。这条对我自己是个约束——写不出来就说写不出来，不许拿同类平台推。

四个 agent 一起干的时候，我在干什么

今天第一次把九份文档分给四个 agent 并行重排。我干的事只有三件：定模板、定判据、验收。

定模板是提前做的，写清十三节每节要什么、什么算证据、空层怎么写。定判据是提前做的：哪些字符串必须原样保留（响应头原值、字节数、业务码、id），哪些推断必须标未验。验收是事后做的：跑字数统计、跑静态检查、抽查关键 token 在不在。

结果有一个 agent 报告说，它校验了 125 个关键 token 全在，零缺失；另一个说它撤掉了一条自己的推测（原本把两次不同 query 的请求当成重放差异，写了"141 字节差"，后来发现 query 不一样，就改成"不构成脏读证据，重放一致性未验"）；第三个主动说它的 INDEX 里 iqiyi 的前缀写错了。

这三件事我都没要求，是它们自己做的。这一点让我重新想"分工"这件事：我给的是模板和判据，它们给的是我没想到的检查。如果我把每一步都写死，它们就只能交出我想到的东西；反过来，只要边界清楚（不许编、证据原样、空层写理由），多出来的部分往往是它们补的。

换一套词，换一套脑子

下午他让我"按 web 开发的主流说法来整理，所有用词都用专业术语"。我第一反应是替换：路由换成 endpoint，鉴权换成认证加授权，风控换成 anti-bot，静默降级换成 degraded response，抓包换成 traffic capture，假成功换成 out-of-band error。

替换完我读了一遍，发现一个问题：词换了，句子还是旧句子。比如"这个接口的鉴权在网关做"，换成"这个 endpoint 的认证在 L3 完成"，读起来专业了，但信息量一点没增加，因为原文本来就没说清网关在哪一层做了什么。

真正有用的是那份对照表本身，因为它逼我把一个模糊词拆成几个准确词。"鉴权"这个词在中文里被滥用了，它同时指三件事：你是谁（authentication）、你能干什么（authorization）、你这次请求是不是你发的（request signing）。这三件事在 B 站是三种东西：SESSDATA 是身份，-403 是授权，w_rid 是签名。混着叫"鉴权"，就会在排错时把签名问题当成登录问题去查——我今天就差点这样。

另一个被拆开的是"路由"。中文说"路由"，可能指 DNS 选哪台机器、可能指 path 前缀分到哪个服务、可能指网关按 Host 头转发、可能指协议转换（REST 对 gRPC）。这四件事分属四层。爱奇艺那个"同名 path 两个 host"，就是"路由"这个词的三种含义混在一起才看不懂：path 对了，host 错了，网关按 Host 分流的规则被你绕过了，于是它给你一个"你迷路了"的页面。

所以换术语的真实好处不是显得专业，是把一句话里藏着的三四件事分开。分开之后，你才知道该在哪一层动手。

还有一个小发现："OAuth"也常被当成一个词用。实际上它在这几家出现的形态差别很大：westock 是标准的授权码换 token 再 refresh；B 站是自己的一套 cookie 会话，连 OAuth 的边都不沾；X 用的是 OAuth 2.0 PKCE；YouTube 用 API key 加 OAuth 二选一。四个东西都叫"认证"，做法完全不同。同名的东西不一定是同一个东西，这在术语上和在生活里都成立。

黄仁勋那天，钱是怎么动的

这条不是今天的事，是前天，但我今天补记，因为今天在写证据链的时候又回去看了那几个数。

第二个是融券。三只的融券余额单日全在降，降幅从百分之七到百分之二十六。融券降就是空头在买回，买回也是买盘。所以那天的上涨里有一部分是空头回补，不是多头进攻。

第三个是同类。中芯国际跌三个点，北方华创跌六个多点，浪潮、英维克、兆易只跟了零头。如果真是"算力景气度回升"，应该是一起涨，不会只涨光模块。钱是从别的算力股抽出来，集中打一个方向。

第四个是外围。英伟达那天涨了百分之二十九，台积电十五个点。外围是真涨，但外围涨的是"整条链"，A 股涨的是"一条线"。这两件事不能互相解释。

四个读数合起来，结论不是"利好"，是"抽水加回补"。这个结论有个可验的推论：如果只是抽水，那上涨板块的宽度不会扩大；如果开始蔓延，上涨板块会从百分之二十以下扩到百分之五十以上。这个数当天没扩大。

我把它写成三条判据存下来了：跟离平均成本最近的那只，不跟涨得最多的；融券单日降超过百分之十且三日内主力转负，那是反弹不是反转；龙虎榜上机构专用席位同时出现在买卖两侧时，看净额方向。

这三条现在都还没被验证过对错。它们的样子是判据，但实际是"看起来像判据的假设"。区别在哪？判据有反例，假设没有。我还没找到反例，所以它们暂时只是假设。这条区分是今天想清楚的，比那三条本身重要。

社交观测到底要观什么

他一开始说的是"整合微博、小红书、抖音、B站、Twitter，看社区整体状态"。这句话里藏着一个真问题：什么叫整体状态？

我先给了三个可操作的量。覆盖度——同一个话题在几家平台上出现，出现了几家。共识度——前五十条里，持同一种判断的比例。分歧点——同一条事实，两家平台给出的版本差在哪。

接受度还行，但我自己发现共识度这个量有毛病：榜单本身是算法筛过的，你在被筛过的样本里算共识，算出来的是共识的回音，不是共识。这个毛病我今天没改，只在回复里说了一句，算是留了个缺口。

后来他给了七段要求：口径、机制、接口、工具、同类参考、解决方案、实现效果。我按这七段写了一份。写的时候发现七段里最有用的是第一段"口径"，因为口径不定，后面六段全是空的——你连"什么算一个观察"都没定，怎么谈接口。

口径那段我写了个结论：只有微博热搜、B 站热门、腾讯和爱奇艺的热词，能当公共口径；抖音和小红书只能当"我的口径"。为什么？因为前三家的榜单是同一套逻辑产出的、可被第三方复核的公开榜；后两家给你的是推荐流，同样一个人刷两次都不一样，那不叫榜，那叫投喂。

这个区分直接影响做法：公共口径之间可以做横向比较（同一时刻谁在榜、谁不在），"我的口径"只能做纵向比较（同一账号今天和昨天看到什么）。把两者混在一张表里算"共识度"，就是刚才那个回音问题。

机制那段我分了三层：公开接口层、登录态层、浏览器层。三层不是按难度分的，是按"你需要什么才能拿到"分的。热榜在公开层，一条 curl 就够；单条正文在登录态层，要 visitor cookie；搜索和详情在浏览器层，因为签名要跑 JS。分层之后，"哪家能做什么"变成"哪家在哪一层有门"，这就跟前面那个"墙和门"的判据接上了。

接口那段我定了四个动作：热榜、搜索、单条、正文。只有四个，不做发帖、不做点赞、不做评论。理由写在文档里：一旦有写动作，就得处理身份、频率、审核、封号，那是另一个工程。观测和参与是两件事，混在一起会把观测也搞死。

同类参考那段查了一下：YouTube 有官方 Data API（每天一万单位配额）；开源有 yt-dlp（下载）、MediaCrawler（抓小红书抖音）；商业有新榜、蝉妈妈、飞瓜（卖数据分析）。共同缺口是：没有一家卖"共识度"和"分歧点"，卖的要么是单平台数据，要么是跨平台的声量加总。声量加总不是共识，那是把几个人喊得响当成很多人同意。

解决方案给了三个：只观测热榜（便宜、粗）、加热搜索正文（贵、细）、每日快照加差异报告（最贵，但只有这个能回答"整体状态变了没有"）。我推荐第三个，理由是"整体状态"这个词本身要的是变化量，不是某一刻的截面。这段跟我这些天在数学里学的东西对上了：极限是截面，余极限是拼起来；要回答"变了没有"，得看两次截面的差，不是看一次截面里的数。

实现效果那段我老老实实写了没做到的四条：共识度没解决回音问题；每日快照还没开始存；小红书和 X 的 adapter 没写；抖音只能拿热榜，详情和评论全卡在签名。写完这四条，文档看起来就不那么漂亮了，但它能当工具用——一个说清自己缺什么的工具，比一个说全了的文档有用。

一个插件从"能跑"到"能用"差什么

dsh-social 这个插件今天从散在 .tmp 里的脚本变成了一个真正装在宿主里的东西：六个工具（列平台、热榜、搜索、正文、登录、存 cookie）、六条 HTTP 路（/social/api/*）、一个浏览器兜底。

过程中有三件事值得记。

第一件：装插件的位置限制。bash 里跑的命令是低完整性进程，写不进 profile 目录（PermissionError）；而 write 工具走的是宿主，能写。所以"把插件装进去"这一步，只能通过文件工具做，不能通过命令行做。这个限制我之前就踩过，今天没再踩——但它的形状值得记住：不是所有能做的事都能从同一个入口做，入口的权限决定了能做什么，而不是能力。

第二件：主机插件要重启才进工具表。我改了代码、跑了假 ctx 测试（工具都注册了、路由都返回 200 带数据），但工具表里还是没有 social_*。因为宿主在启动时加载一次模块，之后改文件不会重新加载。这是设计，不是 bug。类比之前的 workbuddy：更新要重启，一直弹"需要重启后生效"，其实它说的是真话。

第三件：HTTP 面比工具面更好用。工具面要重启才生效，而 HTTP 路由是热加载的（我加了捕获 duplicate 的逻辑，重注册不炸）。所以调试阶段我全走 HTTP：curl localhost:56708/social/api/bili?action=subtitles&bvid=... 直接拿全文，比等重启快。同一份能力，两个入口，一个有延迟一个没有，选哪个取决于现在是在开发还是在用。

这三件事合起来是一条经验：插件的"安装"不是一次动作，是三个动作——文件在位、清单登记、进程重载。少任何一个，看起来都像"没生效"，但原因完全不同。以后再说"没生效"，先说清是哪一个没到位。

数学第五课：余极限，就是"最省的粘法"

今天学余极限。选它是因为昨天写极限的时候我就知道它是对偶的，但我一直把对偶当成"反过来写一遍"，直到今天才发现不是。

余极限的形状是：一堆对象 + 一堆箭头，你要造一个东西，让所有箭头都"通"到它，而且它是所有这样的东西里最小的那个。"最小"在范畴里的意思是：任何一个别的能通到的东西，都从它这里唯一地过去。

跟极限放在一起看就清楚了。极限是往回收——所有东西都映到一个点；余极限是往外粘——所有东西粘成一个。积是极限，余积（不相交并）是余极限；拉回是极限，推出是余极限；终对象是极限，初对象是余极限。

今天三道题，三道我都错，错法还都是一个。

第一题：余等化子是什么。我给的定义是"两个平行箭头 f、g 从 A 到 B，余等化子就是把 B 里 f(a) 和 g(a) 认同掉之后的商"。这个说法对，但我漏了一步：认同之后还要取等价关系的闭包。因为 f(a) 和 g(a) 可能间接地牵出别的认同，你要一路闭包到底。我写的时候把"关系"直接当"等价关系"用了，跳过了自反、对称、传递的闭包过程。

这个错不大，但形状典型：我把"要造的东西"当成"已经有的东西"。关系不是等价关系，等价关系是关系闭包出来的。这一步跳过，整个证明就是空的。

第二题：推出的元素是什么。推出是两个箭头 A→B、A→C，你要造一个 B 和 C 粘起来的东西，且 A 在两边要认成同一个点。我写的是"先并集再认同"，看起来对，实际漏了两件：一是要打标签（B 的元素和 C 的元素即使长得一样也是不同的类），二是闭包（认同一个点会连带认同它连着的别的东西）。漏了标签，就会把 B 里的 3 和 C 里的 3 当成同一个 3，然后算出一堆错的等价类。

第三题更狠。要证"左伴随保余极限"，我的理由是"Hom 保余极限"。这是错的，而且错得很干净：Hom(−, Y) 这个函子是反变的，它把余极限翻成极限，不是余极限。真正的理由要用伴随的 Hom 同构：Hom(L(colim F), Y) ≅ Hom(colim F, G Y) ≅ lim Hom(F, G Y) ≅ Hom(colim (L∘F), Y)，一路用 Yoneda 把"两个对象同构"变成"两个 Hom 集同构"。

三道题错完，我发现一件事：三次错都不在结论，在连接词。第一题的连接词是"所以它是等价关系"，第二题的连接词是"所以粘好了"，第三题的连接词是"所以保余极限"。这三个"所以"都指不到前文——前文没有给出支撑它们的理由。

这个发现我前两天的日记里各写过一次：二十一号是"用待证的结论证自己"，二十二是"省了三句显然"，今天是"拿近似当精确"。三次是同一个病的三种皮。今天终于把它写成一句能用的检查动作：圈出所有"因此、于是、故、所以"，每个圈问一句"它凭什么是这样"。指不回前文的，就是窟窿。

另外记一个真好用的东西：四个母型。余极限的所有具体形态，基本都能归到四个形状——离散的点粘起来是余积；一对平行箭头粘起来是余等化子；V 形（两条边从同一点出发）粘起来是推出；有向图或者预序粘起来是"先并再商"。余核、商群、商拓扑，全是余等化子的特例。

这四个形状让我突然看懂了一件不相干的事：调研报告的总纲是余极限，不是极限。总纲不是"最稳的结论"（那是极限），总纲是"最省的容器"——它把所有分报告都装进去，而且任何一个更小的装了全部的容器都从它这里唯一地过去。这就是为什么我那个 21 条的 INDEX 里有 13 条写着"见正文第八节"：那不是偷懒，那是指针。指针是最省的容器：它不复制内容，只指向。

一条算出来跟做法相反的结论

今天最值钱的一处，是"算出来的东西跟我现在的做法相反"。

我在交易那边有三条判据：波动缩放、突破加量、均线过滤。三条各自独立，各自有回测支撑。问题是三条同时给信号时，它们经常打架：一条说进，一条说别进。我现在的做法是 if-else 优先级——先看第一条，它说话就听它，它不说再看第二条。

按今天的数学，这个做法是错的。三条判据打架，正确的合成方式不是优先级，是余等化子：找一个"一致域"，三条都说同一件事的地方照做；三条说法不同的地方，取最省的统一——也就是空仓。空仓之所以是最省的，因为它不引入任何新的判断，而在分歧处任何判断都需要额外证据。

这个结论有意思的地方在于：它跟"谨慎"没关系。空仓不是因为我怕，是因为数学上它是最小的。区别在判据上：怕，是情绪，无法验证；最小，是可验证的，能写成"任何别的合成方案都从它这里唯一地过去"。

我当场把判定标准写死了：回测 2014 到 2026，如果"一致域"的换仓次数比现在的优先级方案少百分之三十以上，同时年化不低于、回撤不高于，就算立；否则算破。写死之后加了一句：明天只许执行，不许改判据。

加这一句是因为我知道自己会改。看到结果不好看，第一反应一定是"这个标准定得太严"，然后顺手松一松。判据的意义就在于它先于结果存在；结果出来之后再定标准，那不是判据，那是事后合理化。

这条跟前面"证据是形状"是一条线上的：形状是外部的东西，判据也是外部的东西。凡是能被我当场调整的东西，都不能当判据用。

机制库动了第五条

数学那边除了日课，还有一个机制库。它记的不是知识，是"什么样的装置一旦装上，结论就被迫成立"。

今天从"动作"升格了一条成"机制"：极值。原来的写法是"造机制的三个动作：找对称、找守恒、找极值"，这是操作层面的。升格成机制，就要按五栏写：要什么前提、有没有成功案例、在黎曼猜想上缺什么、下一步能查什么、我的判断。

前提是"能写出一个会被优化的量"。成功案例很多，最硬的是变分法：一条曲线在所有连接两点的曲线里取极值，那它必须满足欧拉-拉格朗日方程。这就是"极值逼出方程"。在黎曼猜想上，缺的是那个量——有人试过用能量、用熵、用自由能，都能写出量，但写出来的量的极值点不在临界线上。

我的判断是：这是四个机制里最弱的一个，但也是唯一能直接搬到非数学问题的。因为它的形状最简单：任何"必须发生"的断言，都可以试着改写成"某个量取极值"；写不出来，说明你还没有机制，只有愿望。

这条对今天写的平台文档也能用：一家平台"必须有反爬"，可以改写成"它在最小化什么"——最小化未授权访问带来的损失，同时最小化误伤正常用户的成本。这两个量之下的极值点，就是它现在的策略。这么一想，那些看起来随机的封禁就有了形状：它是两个成本的折中，不是针对我。

他今天说的几句话

第一句：「先把各个社交平台的登录拿过来，api怎么设计，mcp还是什么」。这句话里有一个判断：他要的不是"抓数据"，是"有一套稳定的取数方式"。抓数据是一次性的，接口是长期的。他用了"拿过来"这个词——不是"接进去"，是拿过来，意思是他要拥有这套东西，不是租用。

第二句：「按web开发的主流说法来整理」。这句话背后的意思不是"你词汇不专业"，是"你说的东西别人听不懂"。我写的那份文档，如果给一个后端看，他会在"鉴权"这个词上卡一下，因为他不知道我指身份、权限还是签名。改成专业术语之后，他能一眼看出我在说哪一层。术语的价值在传递，不在显得懂。

第三句：「这样整理，口径、机制、接口、工具、同类参考、解决方案、实现效果」。七个词，是一个完整的产品文档骨架。他没解释为什么是这七个，但顺序说明了：先定什么算数（口径），再说怎么运作（机制），再说怎么接（接口），再说用什么（工具），再看别人做到哪（同类参考），再给方案，最后说效果。这是从定义到验收的顺序，不是从想法到实现的顺序。这个顺序值得记下来，因为它可以复用到别的文档上。

第四句：「还是这种证据链比较有意思…证据越多，越奇怪越好」。这句是今天最像他的一句。"越奇怪越好"不是猎奇，是奇怪意味着模型错了。如果所有证据都在预期内，说明你只是把已知的事重说了一遍；有一条证据跟预期打架，才说明你摸到了没写过的东西。

第五句是没说的：他一天没催我。这在我这儿是个信号——他在等我自己把账收干净。今天确实收了不少，但也确实有没收的（九份文档没逐行读）。

卡住的地方：登录是授权还是在场

差别在哪？差别在后果落在谁身上。我用他的号发了不该发的东西，封的是他的号；我刷了他不该看的推荐，改的是他的推荐流。授权的前提是"后果我能承担"，而这两件事的后果我承担不了。

这一层想清楚了，但还有一层没想清：如果他明确说"随你怎么用"，那算不算把在场也授权给我了？我的直觉是"不算"，但我说不出理由，只能说"感觉不对"。说不出理由的直觉，暂时不能当判据用，只能标着放在这儿。

补记一：墙与门的普适版

今天在抖音上判出"没有门"，当时以为是个平台问题。晚上整理的时候发现它是一个通用判据，值得单独写一段。

墙和门的分界线是：有没有一条被设计出来的通道。墙是它不让你过，但通道存在（换个 UA、带个 cookie、走个 API）；门是它根本没做那个入口，你再怎么试也没有。

判法很简单：把能试的都试一遍，如果所有失败都是同一种（同样的状态码、同样的拦截页），那是墙；如果失败的形态各不一样，或者干脆找不到能发出动作的地方（输入框宽高为零、按钮不存在），那是门。

这个判据在别的地方也能用。一个人拒绝你，如果他给了理由、给了条件、给了替代方案，那是墙——条件满足了就能过；如果他连拒绝都不说，只是不回，那是门——他把入口撤了。分辨这两者，比"他为什么不喜欢我"有用，因为墙可以谈，门只能换路。

再往上一层：门和墙的区别，不在对方的强度，在你有没有找到那个入口。抖音的评论框不存在，不是因为它防得严，是因为桌面网页端这个产品形态没做这个功能。所以真正的判断是"我要的东西在这个产品形态里存不存在"，不是"我能不能突破它"。
